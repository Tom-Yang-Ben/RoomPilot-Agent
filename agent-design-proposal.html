RoomPilot Agent 架構提案 — 討論結論

Master Agent 編排四個 sub-agent，覆蓋「問卷需求 → RAG 選件 → 擺放 → 驗證 → 兩階段生圖 → 改圖 → 設計手冊」全流程。本頁為討論定案版架構提案，不含實作。

2026-07-31 定位：純架構提案文件 來源：image.png（架構草圖）＋ Userflow.png（產品流程） 目標落地：現有八步 FastAPI 產品（不建第二套系統）

1已定案的關鍵決策

以下七點為本次討論拍板的結論，後續章節皆以此為前提。

編排模式：程式固定流程

Master 是 state machine：順序、迴圈上限、暫停點、改圖計數全由程式控制；LLM 只在各 sub-agent 內做語意決策。可預測、好測試、天然支援「可恢復上一動」。

實作框架：文件保持中立，建議自建

skill＝系統提示詞＋流程模板＋輸出 schema；tool＝帶輸入/輸出契約的函式。建議實作為自建 FastAPI + function calling，文字 LLM 經 OpenRouter 可替換。不採 Claude Agent SDK：非授權問題（Anthropic 允許商用），而是模型綁定、固定流程用不到自主迴圈、整合成本。

生圖模型：nano banana，經 OpenRouter 呼叫

與文字 LLM 走同一個 OpenRouter gateway。視角畫面＝Three.js 場景截圖，作為構圖/結構參考連同提示詞送入。改圖僅限一次（成本考量）；生圖失敗上限 3 次，達上限提示失敗原因並改用 nano banana 2——計數與切換均由 Master 強制。

擺放潛規則：語意類，放 agent 層

沙發面向電視、床不正對門、風格一致等語意潛規則放 agent knowledge（軟規則，違反僅警告）；幾何合法性（碰撞/淨空/超界）仍全由 backend/engine/ 判定（硬規則，違反即擋）。

設計手冊：新的統整型手冊，PDF 輸出

Report Agent 產出統整手冊（需求摘要、平面配置、家具清單、材質色卡、逐房渲染圖），以 PDF 格式交付；現有工程文件 MVP 的預算/工序報告併為其中一章。

範圍補齊：A/B 方案＋兩階段生圖

Furniture Agent 以兩種策略產 A/B 兩套擺放方案供擇一；生圖採兩階段：先單房 × 色卡方案比對、使用者選定後才全房生圖（省成本的漏斗設計）。

需求三分流

需求整理必須把問卷拆成：硬約束（尺寸/預算/必備家具）、軟偏好（風格/色系）、家電需求（冰箱/洗衣機/冷氣——依專案契約只進生圖 context，不進 2D/3D 擺設）。

3Master 主流程（state machine）

黃色節點＝human-in-the-loop 暫停點，由 Master 停等使用者輸入後才推進；每個狀態完成即寫入 checkpoint。

修復迴圈：S4 驗證失敗 → 退回 S3 修復（先換位置、再換家具），迴圈上限建議 3 次；超過上限不硬猜，帶著驗證報告回報使用者裁決。迴圈次數由 Master 控制，修復「內容」由 LLM 決定。
生圖失敗政策：單一生圖/改圖請求失敗上限 3 次；達上限向使用者提示失敗原因，並改用 OpenRouter 上的 nano banana 2 重試。失敗計數與模型切換由 Master 控制；失敗重試不消耗「改圖僅一次」的額度。

使用者在 2D/3D 的手動 CRUD 與微調發生在暫停點區間，agent 不介入；結構變更回到平面圖校正步驟時，沿用現行系統的家具重驗機制。

4Sub-agent 職責詳表

Furniture Agent 對應任務 1–3

  • 需求整理 skill：問卷答案 → 需求文件（硬約束／軟偏好／家電 context 三分流）。
  • RAG 家具 tool：需求文件 → 沿用現有 RAG 串聯（BGE-M3＋reranker）檢索排序 PostgreSQL furniture_catalog_current → 候選家具清單（含排序理由）。
  • 挑家具 tool：候選清單＋室內架構＋軟潛規則 → LLM 選件（需求對應、風格一致、尺寸粗篩）→ 家具清單。
  • 擺家具 tool：LLM 產出語意擺位意圖（哪件、哪個功能區、朝向關係，如「沙發面向電視牆」）→ engine 計算合法座標 → 場景配置文件。
  • A/B 方案：以兩種策略各跑一輪（例：動線優先 vs 收納優先）產兩套場景。
LLM 決定需求歸納、選件、擺位意圖、修復方案
不歸 LLM座標與合法性 → engine；檢索排序 → RAG

Validation Agent 對應任務 4

  • 硬規則軌：呼叫 engine API 檢查碰撞、淨空、超界、門窗迴轉——違反即擋，結果是 deterministic 的。
  • 軟規則軌：LLM 讀場景結構化摘要，評語意潛規則（沙發面向電視、床不正對門…）與需求滿足度（雙人床是否真的在主臥）——違反僅警告。
  • 輸出驗證報告：違規清單、原因解讀、修復建議（給 Furniture 迴圈用，也是設計手冊素材）。
LLM 決定違規解讀、修復建議、軟規則與需求滿足評估
不歸 LLM幾何檢查全由 engine；迴圈次數由 Master

Gen_Pic Agent 對應任務 5–6

  • 生圖 skill（兩階段）：階段一產「單房 × 各色卡方案」供比對；使用者選定後階段二全房逐房生圖。
  • 生圖資訊整理 tool：場景配置＋需求文件（含家電 context）＋材質色卡＋視角 → 提示詞包；連同 Three.js 視角截圖（構圖參考）經 OpenRouter 送 nano banana。
  • 改圖 skill：「拿舊圖」取回原圖；使用者意見 → 編輯指令＋鎖定清單（家具位置、材質、視角等不可變元素），明確要求「只改這些、其餘保持」；僅一次，由 Master 計數。
  • 失敗處理：同一請求失敗上限 3 次；達上限提示使用者失敗原因，切換 nano banana 2 重試（失敗重試不消耗改圖額度）。
LLM 決定提示詞組稿、意見轉編輯指令、鎖定清單內容
不歸 LLM成圖 → nano banana（OpenRouter）；次數、失敗 fallback 與階段推進 → Master

Report Agent 對應任務 7

  • 讀全部文件：需求文件、家具清單、場景配置、驗證報告、生圖片、色卡/材質與使用者歷程決策。
  • 組版輸出設計手冊（PDF）：需求摘要 → 平面配置 → 逐房家具清單（含來源與尺寸）→ 材質色卡 → 渲染成果 → 工程與預算章節（沿用現有工程文件 MVP 的 ReportPayload 產出，併為一章）。
LLM 決定各章敘事摘要、決策脈絡整理
不歸 LLM數量/預算計算沿用工程 MVP 既有規則流程

5不可違反的邊界（沿用專案契約）

幾何只歸 engine。家具合法位置只由 backend/engine/ 判定；LLM 不產座標、不判碰撞淨空。
RAG 只檢索排序。家具向量 RAG 只解析需求、檢索與排序資料庫家具，不取代選件決策與幾何判定。
家電不進 2D/3D。冰箱、洗衣機、冷氣等家電需求保留在問卷與生圖 context，不進自動配置與正式家具 API。
資料契約沿用。公分制 _cm／_m2、辨識輸出 layout_json、方案輸出 scene_json；quarantine 資料不進場景。
不建第二套系統。Agent 層嵌入現有 FastAPI 產品流程，重用 Yen 需求/選件、Django RAG、Kai catalog、Ancai engine、Bella 渲染與報告。
成本護欄由程式強制。改圖一次、單房先行的生圖漏斗、修復迴圈上限、生圖失敗三次即提示原因並切換 nano banana 2，全在 Master 的 state machine，不交給 LLM 自律。

7建議實作方向與待辦

建議實作（落地時）

  • FastAPI 內新增 agent orchestrator 模組承載 Master；文字與生圖統一經 OpenRouter 呼叫——文字 LLM 可替換，生圖用 nano banana、失敗 fallback 為 nano banana 2；單一 gateway 便於金鑰與計費管理。
  • skill／tool 依中立定義實作：skill＝提示詞＋流程模板＋輸出 schema；tool＝函式（function calling schema），共用 tool 只實作一份。
  • Agent 狀態與 Docs 全存現有 PostgreSQL project store（revision 控制天然支援「可恢復上一動」）。
  • Ownership 對應：Furniture＝Yen backend/agent/ 擴充（knowledge/select/place 已有雛形）、幾何＝Ancai engine API、RAG＝Django/Kai 現有串聯、Master／Report＝server 層；跨資料夾修改依 AGENTS.md 格式申報。

待辦／後續討論

  • 修復迴圈上限 N 的實測調校（暫定 3）。
  • A/B 兩套方案的策略定義（例：動線優先 vs 收納優先）與提示詞模板。
  • 鎖定清單欄位規格與改圖後的一致性抽查方式。
  • 設計手冊 PDF 版型與排版工具選型、與工程 MVP ReportPayload 的欄位對接。
  • 生圖「未報錯但品質不佳」的判定與處理——API 失敗政策已定（3 次→提示原因→改用 nano banana 2），品質面尚未定義。
  • 各 skill 的評測方式：需求整理正確率、選件對應率、軟規則檢出率。
