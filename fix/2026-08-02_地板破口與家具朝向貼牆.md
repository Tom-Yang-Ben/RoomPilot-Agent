# 2026-08-02 地板破口、家具朝向、靠牆家具不貼牆（修改到他人程式碼的紀錄）

> 本檔記錄「修改到非本人負責模組」的內容，供該模組 owner 覆核。
> 受影響模組：`backend/server/scene_service.py`、`backend/server/static/`（owner 見 `docs/TEAM_AI_OWNERSHIP.md`）。
> 回報來源：使用者回報三個問題並附 `feedback.png` —— ①地板沒有完整填滿整個空間、
> ②家具朝向不對、③該貼牆的家具沒貼牆。
> 測資：floor04 專案（project `1869ca48…`，7 房、19 牆段、5 門 5 窗），實跑資料佐證。

## 問題 1：地板沒有完整填滿整個空間

### 根因

`room_regions` 是**室內淨空**多邊形，相鄰房之間隔著整條牆帶（floor04 實測
相鄰 region 間距 26.9cm，牆體只畫 12cm 厚）。基底樓板
（`scene_viewer.js` `createFloorGeometry`）逐 region 原樣鋪設，因此：

- 每面牆兩側各留約 7cm 完全沒有地板的縫，透出背景；
- **門洞下方整條沒有地板**——牆留了門的開口，region 也沒鋪過去，
  門檻處直接看穿到底（`feedback.png` 每個門口的異常色塊即是門片
  overlay 浮在空洞上）。

後端 region 資料本身正確（7 房環座標與牆段一致），是渲染層鋪法的問題。

### 修復

新增純函式 `expandedFloorSlabRing(ring, bleedCm)`（`scene_visual_contracts.js`，
可測試、不依賴 three）：把 region 外環沿各邊外法線平移後求交（miter offset），
順/逆時針環皆向外。`createFloorGeometry` 以 **14cm** 外擴量鋪基底樓板：

- 26.9cm 牆帶兩側各擴 14cm → 樓板在牆帶中線會合，蓋住牆下與門檻；
- 外牆側 region 邊距外牆外緣 ≥ 20cm → 不會露出屋外；
- **逐房材質 override（`createRoomSurfaceOverrides`）維持未外擴的房間環**，
  材質分界仍在房間線上，只有共用基底樓板外擴。

`synchronizedFloorRegions()` 本身未修改（契約函式，回傳值不變）。

## 問題 2：家具朝向不對

### 根因（三個互相疊加）

本 repo 場景座標的實際朝向慣例是 **rot=0 正面朝 +z**（由三條獨立證據交叉驗證：
`_placement_candidates` 靠牆候選、`_scene_rotation_toward` 的 atan2(dx,dz)、
渲染鏈 world 對 z 鏡像 × rotation 取負 × GLB 原始朝向 -z 兩兩抵銷）。但：

1. `_facing()` 誤用規格文件（y 軸向上）的公式 `(sin, -cos)`，z 分量正負相反
   —— agent 成組候選（床頭櫃貼床頭、椅子在書桌前）全部算到主件**背面**。
2. `_placement_candidates` 多個靠牆候選的旋轉值寫成鏡像：床頭櫃在下牆給 0
   （臉貼牆）、餐椅左右互換（臉朝牆，靠 orientation pass 事後救回）、
   office-chair 第二候選同誤；扶手椅寫死 **-35°** 斜角，2D/3D 看起來像擺歪。
   `_hinted_wall_candidate`（拖曳吸牆）四面牆只有兩個旋轉值（0/0/90/90），
   下牆與右牆的家具背對房間。
3. `orient_layout_toward_targets` 把沙發/書桌也轉向最近的茶几/椅子，產生
   **任意角度**（斜角）且轉完不再驗證合法性 —— 這是 feedback.png 斜擺沙發的來源。

另發現一個隱藏碰撞缺陷：`raster_free` / `raster_commit` 把場景旋轉**未取負**
直接餵進柵格 OBB。場景角與引擎平面角互為鏡像，90° 倍數不受影響，但 45° 拖曳
驗證的是鏡像後的足跡（舊 Shapely 路徑 `_scene_object_to_placed` 一直有取負，
柵格引擎接管時漏掉了）。

### 修復

- `_facing()` 改為 `(sin, cos)` 並補慣例說明。
- 候選表旋轉值逐一修正（床頭櫃 180、餐椅 270/90、office-chair 270、
  扶手椅 270/90 軸對齊）；`_hinted_wall_candidate` 改為上 0/下 180/左 90/右 270。
- `orient_layout_toward_targets`：只轉自由座椅（office-chair、dining-chair、
  armchair），沙發/沙發床/書桌等靠牆件朝向由所靠的牆決定；轉向角**貼齊 90°**，
  旋轉後足跡不變、不需重新驗證。
- `raster_free` / `raster_commit` / 新增的靠牆掃描一律以 `-rotation` 建 OBB。
- payload 出口 `rotation_y_deg` 正規化為 `% 360`（原本衣櫃右牆候選輸出 -90，
  違反契約測試宣告的 `0 ≤ rot < 360`）。

## 問題 3：該貼牆的家具沒貼牆

### 根因

`_placement_candidates` 每個靠牆類型只有**每面牆固定 2-3 個錨點**，錨點被否決後
下一層直接是 **3×3 網格散點**（房間 25%/50%/75% 比例點，全在房間中央）。

floor04 客廳實測（柵格遮罩逐候選重放）：客廳西南角的門有 75cm 通行淨空帶，
恰好壓掉沙發在下牆的 2 個錨點與電視櫃在上牆的 2 個錨點 → 兩者連同茶几全部
落到網格散點：沙發 (346.1,-396.2)=grid(0.75,0.28)、電視櫃 (129.6,-396.2)=
grid(0.25,0.28)、茶几 grid(0.25,0.5)，全部浮在房間中央。

引擎層其實已有完整的靠牆錨定掃描（`backend/engine/rules.py` `try_against_wall`，
規格 §6：長邊優先 × 五定點 + 150mm 步進），但 `generate_layout` 從未接上它。

### 修復

- 新增 `_raster_wall_anchor()`：沿房間輪廓邊（重用引擎 `candidate_edges` +
  `anchor_ts` 的 §6 錨點序列）掃描，背面貼齊可放邊界、正面朝室內
  （`atan2(nx, nz)`，場景慣例版），合法性由**同一套柵格遮罩**（含已放家具）判定。
  插入在「類型錨點失敗之後、網格散點之前」，僅對 `_WALL_ANCHORED_TYPES` 生效。
- `build_raster_context` 對輪廓環做**方向正規化**（有向面積 < 0 則反轉）：
  Shapely `buffer` 的外環是順時針，而引擎 `Edge.inward()` 約定「室內在左」
  （逆時針）——不翻轉的話內法線全指向房外，掃描永遠失敗。
- 方案 B 的候選反轉改為**只反轉類型錨點、網格散點維持最後**：原本整串反轉
  讓 B 案的靠牆家具直接從房間中央的網格點開始試，永遠貼不了牆。

### floor04 全屋重放（修改前 → 修改後）

## 未處理／後續

1. **正俯視左上角的 2D 窗戶記號畫在建築外**——已確認不是 3D 網格
   （全場景僅 shadow-ground 超出牆範圍），是某層 2D 標註 overlay 的投影問題，
   與本次三項修復無關，需另案處理。
2. **`backend/engine/rules.py` 的朝向公式是規格 y-up 版**（`facing_deg`/
   `front_vector` = `(sin, -cos)`），與本 repo z-down 場景資料相反；目前產品路徑
   只用它的錨點序列與 OBB（不受影響），但若日後把 `RULES` 房型規則直接接進
   scene_service，z 向牆的朝向會鏡像。建議 Ancai 在 rules 層明確標註座標框。
3. **扶手椅與書櫃仍落在最大區域**（`ROOM_AFFINITY` 刻意缺項，見前次報告），
   它們也因此常駐「未指定空間」清單。要不要補 affinity 屬需求決策。
4. 電視櫃由掃描落在長邊優先的合法牆位，不保證在沙發正對面；規格 §7.1 的
   「對面平行牆」規則仍待接入（現行僅 agent hints 路徑有成對邏輯）。
5. 本分支 `test_scene_v2_contract` 既有的 13 個 stale 失敗（cache key、UI 字串）
   未一併整修——那是獨立的欠帳，混進本次會蓋掉真正的行為差異。
