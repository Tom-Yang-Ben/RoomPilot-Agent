## 2. 定位與不做的事

**一句話定位:** 即時提案溝通平台。把使用者的平面圖與需求,在幾分鐘內變成可依風格自動擺位、可手動微調的 3D 提案畫面,讓設計師與客戶快速對齊想像。

**明確不是(Out of Scope):**

- 不取代 AutoCAD / 3D Max 施工圖。
- 不做純炫技、無法驗證的 AI 生圖(避免視角幻覺、空間不一致)。**也不做自然語言換風格。**
- 不做硬裝(天花板/管線/結構)、不做水電消防法規。
- 不做任意 CAD/PDF 全自動解析。
- 不追求寫實渲染與任意角度生圖。

## 4. 核心流程(主線,7/7 改版)

```
需求收集:一般需求(問卷勾選) + 特殊需求(自然語言 → LLM 轉成 JSON)
  → 上傳平面圖(DXF / PNG;JPG 類為 P1)
  → 使用者手動拉比例 / 校尺寸(單位:公分)★ 新增步驟,升維前必經,尺寸才會準
  → 空間升維 3D 白模(可旋轉縮放)
  → AI Agent 依需求 + 風格擺位家具(不同風格 → 不同擺位;風格由風格界定 JSON 定義)
  → 手動微調(拖曳,MVP)/ 自然語言微調(P1 加分)
  → 3D 提案畫面 → 多輪迭代
```

**兩個關鍵設計:**

1. **需求拆兩層**:一般需求(人數/預算/風格偏好等)用**問卷勾選**直接收,不勞駕 LLM;**特殊需求**(自由文字)才用 LLM 辨識轉成 JSON,餵給 Agent 擺位與風格生成。~~client_brief~~ **已廢除**,由「問卷結果 + 特殊需求 JSON」取代。
2. **風格 = 界定 + 擺位** 兩件事分開:**舒媁做風格界定**(家具風格設定 JSON、12 風格資料庫 —— 定義每種風格用哪些家具/材質/色彩),**柏彥的 Agent 做擺位**(依風格與需求決定放什麼、放哪裡,不同風格有不同擺位邏輯)。不做 ControlNet/圖像生成路線。

## 6. AI Agent 與引擎

### 6.1 Agent 做什麼(7/7 改版)

**柏彥的 AI Agent = 家具擺位 + 風格生成**:吃「一般需求(問卷)+ 特殊需求 JSON」,依選定風格決定放什麼家具、怎麼擺 — **不同風格要能生成不同的擺位方式**。風格的內容(哪些家具、材質、色彩屬於哪種風格)由**舒媁的風格界定 JSON** 定義,Agent 讀它來選件。

### 6.2 引擎工具 + 現況

| 引擎     | 工具名                                            | 做什麼                                 | 現況                                         |
| -------- | ------------------------------------------------- | -------------------------------------- | -------------------------------------------- |
| 空間升維 | `upgrade_to_3d`                                 | (前置:手動拉比例)2D 平面圖 → 3D 白模  | 🟡 管線已整合;手拉比例未做、窗戶顯示有問題   |
| 基礎配置 | `place_furniture`                               | 依需求放真實尺寸家具                   | 🟡 邏輯有、測試過;房間尺寸錯誤 → 實際未完成 |
| 軟裝微調 | `adjust_furniture`                              | 手動拖曳(MVP)/ 自然語言(P1)調位置,重繪 | 🔴 手動微調未修好;碰撞規則未劃分完           |
| 風格擺位 | (Agent 內建,tool schema 沿用`engine/schema.py`) | 依風格界定 JSON + 需求 → 選件與擺位   | 🔴 未做                                      |

> 介面契約:`roompilot/engine/schema.py` 的 `PLACE_FURNITURE_TOOL` / `ADJUST_FURNITURE_TOOL` 仍是 Agent ↔ 引擎的對接基礎;`examples/demo_agent_flow.py` 有 id 規則與失敗詞彙表。LLM 串接走 OpenRouter;**凡直接動到 LLM 的實作工作皆由楊舒媁負責**(key 由柏彥統一控管,制度為舒媁提議)。

### 6.3 碰撞 / 重疊 / 動線規則(承安,劃分中)

現行引擎把「碰撞」一律視為違規,這不對 — 要劃分**合法重疊**:

- **電視** 應該可以放在**電視櫃上**(上下疊放合法)。
- **地毯** 應該可以墊在**所有家具下面**。
- 其他類似的家具疊放組合,由承安逐類劃分規定。
- **擋門檢查:未做。動線規劃:尚未明確規範。**

## 8. 資料結構

- **一般需求(問卷結果):** 勾選項(人數、預算、風格偏好、機能等),前端直接結構化,不經 LLM。
- **特殊需求 JSON:** 使用者自由文字 → LLM 辨識轉成 JSON(🔴 未做),餵 Agent 擺位/風格生成。
- **風格界定 JSON(舒媁):** 家具風格設定(目標 7,000 件)+ 12 風格資料庫 — 定義風格 ↔ 家具/材質/色彩的對應,Agent 選件的依據。
- **平面圖辨識輸出:** 牆段線段(座標)→ 手動拉比例校正(公分)→ 升維管線。
- **資料庫:** `PROJECT 1—N FURNITURE`(擺放實例掛 project_id)+ 需求 JSON 存放;**擺放屬性必要欄位:`pos_x` / `pos_y` / `rotation`**(對應 `schema.py` 的 `placed_to_dict`)。Redis 暫存層規劃中未接。
- **尺寸單位:對外(顯示/輸入/資料交換)一併改成公分**;引擎內部單位是否跟改,落地時對照 CLAUDE.md 單位契約再定。

## 9. 平面圖辨識(現行真實能力)

離線、不需 LLM。

- **DXF:** 🟢 解析 LINE / LWPOLYLINE / POLYLINE / ARC / CIRCLE / MLINE → 牆體;門 L 形+弧偵測、窗開口覆蓋率偵測;窗 精準 89% / 召回 91%、門 過濾 ~100%。
- **PNG:** 🟢 **已做,成功率高**(灰階二值化 → 形態學 → 牆遮罩向量化 → 正交化輸出 DXF)。
- **JPG / JPEG / BMP:** 🟡 已做,**成功率僅 ~50%** — **非 P0**,列 P1 續改。
- **驗證資料:** `testdata/`(png 20 張 + 答案、door 19 樣式、dxf 29 個;floor21 為 Demo 基準圖,待從 cody 分支移植)。

**限制:** 圖片無真實單位 → **必須靠 F2a 手動拉比例校正**;牆以軸向為主,斜/弧牆會掉。

## 16. 驗收標準(8/20,隨新方向調整)

**功能驗收**

| 項目             | 通過標準                                                                              |
| ---------------- | ------------------------------------------------------------------------------------- |
