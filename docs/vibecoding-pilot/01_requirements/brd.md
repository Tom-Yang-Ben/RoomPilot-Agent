## 2. 現行流程 (As-Is)

repo 內**沒有**任何「導入 RoomPilot 前」業務流程的訪談紀錄或制度文件。本節由 2026-07-26 版 PRD 草稿的問題陳述反推，屬推測性描述；下表逐列標註（未查證），待訪談或業務 owner 確認後改寫。

```mermaid
flowchart LR
    A[屋主取得建商平面圖] --> B[口頭或文字向設計師描述需求]
    B --> C[設計師人工繪製 2D/3D 與渲染圖]
    C --> D[屋主審閱並往返修改]
    D --> B
    D --> E[方案定案]
```

| 步驟 | 執行者 | 工具／系統 | 痛點 |
| :--- | :--- | :--- | :--- |
| 描述空間現況與生活需求 | 屋主 | 口頭、紙本平面圖 | 不易把需求講清楚（未查證，沿用 PRD 草稿問題陳述） |
| 確認格局、風格與家具 | 屋主＋設計師 | 面談、通訊軟體 | 往返確認耗時、成本高（未查證，同上） |
| 繪製配置與提案圖 | 設計師 | 人工繪製 2D/3D 與渲染 | 製作耗時，修改一次重畫一次（未查證，同上） |

### 2.1 待訪談確認事項

As-Is 缺口需由業務訪談補齊，重新提案前先確認：

- 目標用戶是「屋主自助」還是「設計師帶著屋主用」？兩者的付費意願與使用場景不同（repo 內兩種說法並存，皆未查證）。
- 現行人工流程一輪提案實際耗時多久？往返幾次？——沒有這個基線，預期效益永遠無法量化。
- 成果發表之後，本專案是否有商轉或續作規劃？（影響第 3 節過渡期策略是否需要補寫。）

## 3. 未來流程 (To-Be)

RoomPilot 的正式流程稱「八步流程」：主畫面固定八個步驟按鈕（本輪已對現行網頁核對），前面有登入與「我的專案」選擇專案，後面接「成果報告與明細」頁。**步驟清單的唯一權威是 `README.md`「現行八步流程」段**；細部流程圖、逐步確認與回退規則見 [使用者流程與系統架構圖](../../使用者流程與系統架構圖.md)。本節只畫業務摘要，不重抄步驟表。

```mermaid
flowchart LR
    A[建立專案並上傳平面圖] --> B[確認尺寸與空間結構]
    B --> C[表達全屋與逐房需求]
    C --> D[AI 配置家具並同步編輯 2D/3D]
    D --> E[鎖定方案與生圖視角]
    E --> F[AI 渲染成果與報告：採購明細＋工程估價]
```

- **與 As-Is 的關鍵差異：**
  - 自動化了原本設計師人工執行的段落：平面圖辨識、家具選件與擺位、寫實提案圖產生。
  - 使用者可全程自助；設計師的角色從「代工繪圖」轉為「在同一畫面與客戶確認方向」。
  - 新增 As-Is 沒有的成果報告：設計風格語彙、家具採購明細、工程施工費與初步工期（`README.md` 第 9 步說明）。
  - 保留人工把關點：尺度校正、空間結構確認、家具擺放調整都由使用者確認，AI 不越過使用者拍板（[使用者流程與系統架構圖](../../使用者流程與系統架構圖.md) §6 回退規則）。
- **過渡期並行策略：** 不適用——本專案為新建課程專題，無既有系統需要切換。若未來走向正式營運，導入與並行策略尚未規劃（TO-BE，未查證）。

### 3.1 使用者最終取得的交付物

| 交付物 | 內容 | 依據 |
| :--- | :--- | :--- |
| 可恢復的專案 | 流程可中斷、重新登入後從上次進度繼續；專案可分享給其他帳號共同檢視或編輯 | `README.md`「帳戶端」段 |
| 2D/3D 家具配置 | 同一畫面同步編輯 2D 與 3D、走動預覽；方案以 A/B 兩案比較 | `README.md` 第 6 步；[使用者流程與系統架構圖](../../使用者流程與系統架構圖.md) §1 |
| 逐房渲染成果 | 依問卷、家具、材質、色卡與鎖定視角產生的逐房 AI 生圖 | `README.md` 第 8 步 |
| 成果報告與明細 | 設計風格語彙、家具採購明細、工程施工費與初步工期；採購與施工為兩筆獨立預算（BR-004） | `README.md` 第 9 步說明 |

## 4. 業務規則 (Business Rules)

以下規則已寫入系統行為與團隊協作守則（來源欄為可查證座標），但**尚未有業務 owner 的正式核准紀錄**——需求追蹤簿本輪 Pilot 導入不實例化，優先序與例外的最終裁量待 owner 於追蹤簿①拍板（硬閘規則見 `VibeCoding_Workflow_Templates/_meta/workflow_manual.md` §8，此處只引用不重述）。

| ID | 規則 | 例外情境 | 來源 |
| :--- | :--- | :--- | :--- |
| BR-001 | 未處理的家具碰撞、淨空不足、超出邊界或模型載入問題，會阻擋使用者進入下一步 | 使用者可改選、移動或刪除該家具後續行 | `README.md`「現行八步流程」段 |
| BR-002 | 牆、門、窗、樑、柱大幅變更必須回到第 4 步重新確認，系統重新驗證目前家具 | 無——結構正確性優先於進度 | `README.md`；[使用者流程與系統架構圖](../../使用者流程與系統架構圖.md) §6 |
| BR-003 | 冰箱、洗衣機等家電需求只保留在問卷，供第 8 步 AI 生圖反映，不進入 2D/3D 自動擺設 | 無 | `README.md`「家具資料與 PostgreSQL」節；[現行版本總覽](../../RoomPilot_現行版本總覽.md)「家具、家電與資料庫」節 |
| BR-004 | 家具採購與工程施工費是兩筆獨立預算，成果報告分開列示、不予合計；查無價格的品項不以已知小計冒充總價 | 無 | `README.md` 第 9 步說明；`AGENTS.md`「不可違反的契約」 |
| BR-005 | 成果報告中的設計風格語彙屬團隊編纂知識，報告如實標示其信心程度（上限「中等」）；報告數字一律來自鎖定版方案與工程知識庫 | 無 | `README.md` 第 9 步說明；`AGENTS.md`「不可違反的契約」 |
| BR-006 | 專案一律有擁有者。設計師角色可建立、編輯專案並鎖版出報告；客戶角色只能檢視被分享的專案；管理員可跨帳號維運。分享成員分「可編輯」與「唯讀」；未被分享者不會得知專案存在 | 無 | `README.md`「帳戶端」段；`AGENTS.md`「不可違反的契約」 |
| BR-007 | 忘記密碼無自助信件流程：由管理員設定臨時密碼並口頭告知，使用者登入後自行修改；改密碼成功後所有既有登入立即失效，需重新登入 | 無 | `README.md`「帳戶端」段 |
| BR-008 | 第一個註冊的帳號自動成為管理員，並收養帳戶功能上線前建立的既有專案 | 正式部署須在開放註冊前先建好管理員，或關閉此自動行為（此點同時列於資安待辦） | `README.md`「帳戶端」段 |
| BR-009 | 管理員停用帳號立即生效（無法登入、既有授權全部失效）；管理員不能停用自己 | 無 | `README.md`「帳戶端」段 |
| BR-010 | 隔離區或未匹配的家具資料不得出現在正式選件、畫面或提案 | 無 | `AGENTS.md`「不可違反的契約」；[現行版本總覽](../../RoomPilot_現行版本總覽.md) |
| BR-011 | 第 6 步正式家具以團隊維護的正式資料庫為優先來源；資料庫暫時不可用時，才退回 repo 內已驗證的備援清單。改用備援清單由團隊操作明確指定，系統不自行切換；資料庫不可用時系統會如實回報並暫停家具選件（守則原文的「才退回」語感與現行系統行為的落差，列為待確認——多來源不一致） | 離線開發可明確指定使用備援清單 | `AGENTS.md`「不可違反的契約」；`README.md`「家具資料與 PostgreSQL」節 |
| BR-012 | 家具無法合法放入時不硬塞：顯示原因、提供較小同類替代品，或交由使用者在第 6 步手動處理 | 無 | [使用者流程與系統架構圖](../../使用者流程與系統架構圖.md) §6 回退規則 |
