## 1. 背景與問題

- **上下文**: `frontend/site.css` 是正式前端唯一的共用樣式檔，現為 17,679 行（2026-08-07 `wc -l` 實測；2026-08-03 裁決當時約 15.6k 行，其後持續成長）。前端不經打包，以原生 ES module 直接載入（README.md:289-290，實讀）。
- **問題**: 大型單檔 CSS 在盤點時容易被提案「按頁拆分」以求可讀性與載入效能；需要裁決拆或不拆。
- **驅動因素/約束**:
  - 無 build step——repo 明文「前端不經打包」，任何拆分都是手工搬移，無工具保證等價。
  - 大量同權重規則靠原始碼順序決勝，重排順序的回歸完全靜默。
  - 專案無視覺回歸（截圖比對）護欄。

## 2. 考量的選項

### 選項一: 按頁拆分 site.css
- **描述**: 依 index／projects／scene 等頁面把規則拆成多檔，各頁只載自己的。
- **優點**: 單檔行數下降；表面上冷訪問少載無關規則。
- **缺點**: cache key 收斂後各頁引用同一 hash、瀏覽器只載一次，效能收益趨零；同權重規則重排的回歸靜默且無護欄；無 build step 可做零風險拆分。
- **成本/複雜度**: 高（風險主導）

### 選項二: 維持單檔，投資方向改為清理死選擇器
- **描述**: 不拆檔；CSS 的整理性投資放在移除死鏈選擇器與孤兒樣式。
- **優點**: 零重排風險；已有實際落地（commit `14c680cf`，2026-08-03 chore(frontend): 清除 site.css 視覺問卷死鏈的孤兒樣式）。
- **缺點**: 單檔行數持續成長，可讀性問題未根治。
- **成本/複雜度**: 低

## 3. 決策

**選擇**: 選項二。2026-08-03 Ben 裁決 site.css **不做**按頁拆分（工作階段記錄，repo 外；正式書面紀錄——未查證）。理由三點：

1. cache key 收斂後七頁引用同一 hash、瀏覽器只載一次，拆分的效能收益趨零。
2. 上萬行同權重規則靠原始碼順序決勝，無截圖比對護欄之下，拆檔重排順序的回歸完全靜默。
3. repo 明文「前端不經打包」（README.md:289-290），無法用 build step 做零風險拆分。

同日的死選擇器清理 commit `14c680cf` 是選項二投資方向的實作證據。

## 4. 後果

- **正面**: 避免一次高風險、低收益的重構；CSS 整理投資導向可驗證的死碼清理。
- **負面**: `site.css` 持續成長（裁決時 ~15.6k 行 → 2026-08-07 實測 17,679 行）；新樣式仍疊加在單檔上，可讀性債持續累積。
- **影響範圍**: `frontend/site.css` 與引用它的各頁；ui_spec 的樣式交付方式。
- **重新評估觸發（裁決時同步訂下）**: 兩條件**同時**成立才重議——(1) 建立截圖比對護欄；(2) 冷訪問效能成為量測到的真需求。
- **憑證缺口**: 本決策在 repo 內無 ADR、無 `.out-of-scope/` 檔（該目錄現只收 `.claude` 生態系機制，2026-08-07 實查無 site.css 相關檔）；唯一書面憑證是 repo 外工作階段記錄。**本 ADR 即是把它正式化的第一份 repo 內文件，內容待 Ben 確認。**
