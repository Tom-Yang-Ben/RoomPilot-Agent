# 專題定義釐清

日期：2026-07-03

## 一句話版本

我們專題不是要「無中生有生成全新的 3D 家具模型」。

我們專題真正要做的是：

**根據使用者提供的平面圖、風格需求與既有 GLB 家具資料庫，自動生成可展示的 3D 室內配置場景。**

## 這份專題到底在做什麼

系統流程應該理解成：

1. 使用者輸入平面圖或空間資訊。
2. 系統依平面圖建立 3D 空間結構，例如牆面、房間邊界、門窗位置。
3. 使用者選擇風格，或輸入需求文字。
4. 系統根據風格規則、尺寸限制與家具資料庫，自動挑選合適家具。
5. 系統把既有 GLB 家具放進 3D 場景。
6. 最後在網頁中用 Three.js / FastAPI 呈現結果。

## 不是什麼

這個專題目前不是：

- 讓模型自己憑空生成全新家具模型
- 完全不依賴家具資料庫的 text-to-3D
- 純文生 3D 家具
- 單純做 moodboard 展示網站

## 為什麼需要家具資料庫

家具資料庫不是可有可無，反而是這個專題的核心基礎。

家具資料庫的用途包括：

1. 作為場景配置的真實家具來源
   - 系統不是亂生家具，而是從既有 GLB 庫中挑選家具。

2. 作為風格對應基礎
   - 每件家具要知道自己偏哪些風格，系統才知道北歐風、工業風、輕奢風各自適合放哪些家具。

3. 作為空間配置依據
   - 家具尺寸、可否旋轉、是否靠牆、是否擋門窗、是否影響動線，都需要資料庫欄位支撐。

4. 作為前端展示資產
   - 網頁最後顯示的 3D 家具，來自資料庫裡的真實 GLB，不是卡通示意，也不是模型亂生成。

## 「自動生成 3D」在這個專題裡的正確意思

這裡的「生成」應該理解為：

- 生成 3D 空間骨架
- 生成家具配置方案
- 生成完整 3D 場景結果

不是：

- 生成全新家具模型本身

所以更精準的說法是：

**這是一個以平面圖、風格規則與家具資料庫為基礎的 3D 場景自動配置系統。**

## 風格生成在這裡扮演什麼角色

風格生成不是獨立存在的裝飾工作，而是整個系統的中介層。

它的作用是：

1. 把抽象風格變成可被系統理解的結構化資料
2. 建立「風格 ↔ 家具」的對應關係
3. 讓 LLM 或規則系統能根據需求挑家具
4. 讓場景生成結果不是亂擺，而是有風格一致性的配置

## 訓練與 VRAM 的位置

如果只是做：

- 風格資料整理
- 家具資料庫建置
- GLB 對應風格
- 平面圖拉牆
- 家具自動擺位
- FastAPI + Three.js 展示

通常不一定需要自己訓練模型。

但如果未來想升級成更強的自動化，例如：

- 系統更智慧地理解平面圖
- 更自動地決定家具配置
- 自動判斷更複雜的空間設計規則

才比較可能逐步需要更高的模型能力與更高的 VRAM。

## 最終對外說法

如果要對老師、組員或外部說明，建議用下面這句：

> 我們專題不是生成全新的家具模型，而是根據使用者平面圖、風格需求與既有 GLB 家具資料庫，自動生成 3D 室內配置場景，並在網頁中互動展示。
