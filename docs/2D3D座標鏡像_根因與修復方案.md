# 2D 平面圖與 3D 白模「上下鏡像」：根因分析與修復方案

- **狀態**：提案，尚未動工（本文件供 review，拍板後再改程式碼）
- **日期**：2026-07-26
- **調查方式**：Playwright 實際操作頁面比對 + 全程式碼座標流追查（非純看碼推測）
- **影響頁面**：`scene_lab.html`（擺位工作台）與 `scene.html` 主流程（共用 `scene_viewer.js`），兩者同病

---

## 1. 現象（已實測確認）

以專案 `b787b05d...`（GROUND FLOOR 底圖）實測，在頁面上逐一選中家具比對 2D 面板與 3D 俯視：

| 物件 | 2D 平面圖（底圖為準） | 3D 俯視實際位置 |
| :--- | :--- | :--- |
| 雙人床 | DORMITORY，左上 | 左**下**房間 |
| 單門冰箱 | KITCHEN，右上 | **下**方中間 |
| 滾筒洗衣機 | BALCONY，左下 | **上**方條狀區 |
| 沙發/茶几/電視櫃 | LIVING ROOM，右下 | 右**上**房間 |
| 玄關 | 廚房門弧在右上角 | 右**下**角 |

**每一件都是上下顛倒、左右不變** → 這是「鏡像」不是「旋轉 180°」（旋轉會連左右一起翻）。
鏡像是手性翻轉，**轉相機救不了**，幾何本身的軸向就反了。

兩邊各自內部都是一致的：床在 3D 的「臥室」裡、冰箱在 3D 的「廚房」裡（牆、家具、玄關一起翻），
所以引擎擺位驗證不會報錯——但以平面圖為 ground truth，**3D 白模是一間手性相反的鏡像屋**，
走路模式走起來房間相對方位與真實格局相反；`exportGlb` 匯出的 GLB、`capturePng` 送遠端渲染的
參考圖也都是鏡像的。

### 關鍵數據佐證

- 平面有效尺寸：733 × 806 cm（bbox 833×916 px × 0.88 cm/px）
- 雙人床 `position_cm = {x: −178.87, z: +277.36}`；臥室 polygon y = 478.6 ~ 788.4
- 臥室在底圖是「最上面」但 polygon y 值接近最大 → **座標系 y 朝上（原點左下）**
- 2D 面板繪製時有翻轉（床畫在距頂 15.6%，正好 = 1 − 680.4/806）→ 2D 正確
- 3D 把 z 直通給 three.js、topdown 相機 +z 畫在螢幕下方 → 3D 鏡像

## 2. 根因：z 軸正方向從未被契約定義

座標流全鏈路（file:line 以本分支為準）：

1. **引擎 frame**：`backend/engine/models.py:9-12` 明文定義——公分、X 向右、**Y 朝上**、
   原點平面圖左下；rotation 逆時針、0° 朝 +Y。
2. **組裝點**：`backend/server/scene_service.py` `generate_layout()` 轉 sceneData：
   `x = pos_x − half_w`、**`z = pos_y − half_d`（不變號，L981、1342-1344、1491-1492）**、
   `rotation_y_deg = (−rotation) % 360`。docstring（L1233-1235）寫了置中原點與旋轉取負，
   **但沒寫 z 的正方向**。
3. **2D 端全部有翻**：`scene_layout2d.js:298`（`planCmToLayerPixel`）、`scene_v2.js:1319-1333`
   （`cmToPixel`/`pixelToCm`，結構/標註/問卷平面全走這裡）→ 2D 正確。
4. **3D 端直通**：`scene_viewer.js:2925-2927`（家具 `position.z = position_cm.z`、
   `rotation.y = +deg`）、`createRoom` L1949 起（牆/門窗/樑柱/地板全部原樣吃 z）→ 鏡像。

**契約缺口**：查遍 `docs/contracts/`、engine README、各 docstring——單位（cm）與原點
（置中 vs 角落）契約完備，**唯獨 z 正方向沒有任何文件定義**。
`backend/engine/README.md:30`「pos_y 對應前端 three.js 的 z 軸」這句缺了負號說明，是誤會源頭。

### 加重因素：repo 裡有兩種互相矛盾的產生端慣例

| 進料路徑 | z 慣例 | 3D 顯示結果 |
| :--- | :--- | :--- |
| 影像辨識/編輯器（主流程） | y-up 直通（`floorplan_from_editor_payload`，scene_service.py:977-982 無翻轉） | **鏡像**（本次實測） |
| DXF 匯入 | 已翻轉——`_flip_parsed_z`（scene_service.py:1510-1541），docstring 明講「three.js +z 朝南，在來源處翻一次」 | 正確 |

另外 **`frontend3d/` 已是正確範本**：`Scene.jsx:7-9` 註解明寫 `worldZ = -z`，
進 3D 翻、出 3D 逆翻、互動（pick plane、snap）全程一致。`scene_viewer.js` 要做的就是同一件事。

## 3. 修復方案

### 方案 B（推薦）：viewer 邊界統一變換，引擎契約不動

原則：`position_cm` / `rotation_y_deg` / sceneData **永遠保持引擎座標**；
three.js 世界 = 進場 `z → −z`、`旋轉 → −旋轉`，流出時做逆變換。
引擎、2D 面板、layout_2d 資料、已存專案（影像路徑）全部零修改。

修改點清單：

| 檔案 | 修改 | 規模 |
| :--- | :--- | :--- |
| `frontend/scene_viewer.js` | flip helper + 進場 ~6 處（loadScene 幾何、家具 2925-2927 / 2858-2860、snap 3763-3778、walk 3078-3141）＋出場 ~8 處（拖曳 3954-3966、beginPlacement 3576-3580、樑 3549-3566、wrapperPositionCm 4005 / scenePositionCm 4109、/api/scene/layout·validate 進出 3874-3894 / 3515-3533） | ~16 點，各 1-3 行 |
| `scene_structure_geometry.js` | `structurePreviewDescriptor` L418-421 centerZ 翻轉 + 角度取負 | 2 處 |
| `scene_structure_preview.js` | L79-82 startZ/endZ 翻轉（L92 atan2 會自動修正） | 2 處 |
| `scene_v2.js` | `roomCameraSuggestion` L7245-7254 z 翻轉 + import cache-key | 2 行 + key |
| `scene_lab.js` / `scene.js` | 只更新 `?v=sha256` cache-key | 各 1 行 |
| `backend/server/scene_service.py` | 統一產生端：移除 `_flip_parsed_z`（或依 `floorplan.source` gate，見待決 #1） | 1 函式 |
| `backend/engine/README.md`、`docs/contracts/` | 補 z 方向契約（明訂：sceneData z = 引擎 y、y 朝上；viewer 負責翻轉） | 文件 |
| `tests/` | cache-key 對照測試更新；建議加方向回歸測試 | 小 |

順風因素：
- topdown 相機 `up=(0,0,−1)`（scene_viewer.js:2516）翻轉後**自動**與 2D 對正，不用改。
- 既有絆線測試（`test_scene_v2_contract.py:300-349、571-586` 等）錨定「資料 frame 不得變」，
  剛好強制修法只能落在 viewer 邊界，與本方案同向。
- 宿主頁 callback（含 3D 加樑寫回 `scene_v2.js:6249-6281`）因逆變換做在 viewer 出口，不需要改。
- 驗收工具現成：調查用的 Playwright 腳本可直接重跑（床/玄關方位、拖曳 round-trip）。

### 方案 A（不推薦）：改產生端輸出 three.js frame（z = y 朝下）

`scene_service.py` 各轉換點加翻轉、2D 共用模組 `planCmToLayerPixel` 移除翻轉、
2D 拖曳反號、**所有既存影像路徑專案的 sceneData / layout_2d / 相機快照需要資料遷移**。
波及範圍與風險都大於方案 B。

### 已否決的捷徑

- 根節點 `scale.z = −1`：raycast/拖曳座標域分裂、GLTFExporter 把負縮放烘進 GLB、
  非對稱家具（如 L 型沙發）變鏡像。
- 只調相機：鏡像不是旋轉，數學上不可能。

## 4. 待決事項（需要組員拍板）

1. **DXF 專案怎麼處理**：移除 `_flip_parsed_z` 讓所有 sceneData 統一 y-up
   （若 store 有既存 DXF 專案需一次性 z→−z 遷移），或給 sceneData 標來源、viewer 依來源決定翻不翻。
   前者乾淨。請先確認實際有幾個 DXF 專案。
2. **舊相機快照**：`masterView` / `roomViews`（會送 render-jobs）是對著鏡像世界取的景，
   修正後同一顆相機拍到相反側——接受一次性視角跳動，或做快照遷移。
3. **分工**：`frontend/` 修改由前端負責人執行；引擎側契約文件由 ancai 補寫。

## 5. 驗收方式

1. 重跑 Playwright 比對：床 2D/3D 都在左上、玄關都在右上、洗衣機都在左下。
2. 非對稱家具手性：2D CSS `rotate(+deg)` 與 3D 翻轉後 `rotation.y = −deg` 朝向一致。
3. 拖曳 round-trip：3D 拖動 → 引擎驗證 → 寫回 → 2D 同步，座標不漂移、不二次翻轉。
4. `exportGlb` 匯出與平面圖同向；DXF 場景（若有）不被弄反。
