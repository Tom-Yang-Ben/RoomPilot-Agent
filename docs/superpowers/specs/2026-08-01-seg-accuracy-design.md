# 灰階切割層純幾何調優 — 設計文件

- **日期**：2026-08-01
- **分支**：cody
- **狀態**：待使用者核准

## 背景與動機

v2.22 詞彙統一後，own_eval 12 題保留集的端到端全對率為 49/72 = 68.1%。
損失拆層（2026-08-01 實測，`report_own_current.json`）：

| 層 | 損失 | 現況 |
| :--- | ---: | :--- |
| 切割層（IoU≥0.5 配對失敗） | 17 間 | 命中 55/72 = **76.4%**，配對平均 IoU 0.875 |
| 命名層（配對上但叫錯） | 6 間 | 55 間中對 49 = 89.1%（GT 分割模式 63/72 = 87.5%） |

切割層損失約為命名層 3 倍，且切割失敗的房間命名層完全救不到——
Readme「已知待辦」早已記載「分割層仍是最大瓶頸」。本輪先攻切割層，
命名層之後另開一輪。

## 目標（成功標準）

**own_eval 12 題保留集切割命中率 ≥ 95%（≥69/72）**，即 17 個漏切最多剩 3 個。

- 誠實聲明：這是進取目標。若歸因分析顯示多數漏切屬圖面本質難點
  （如開放式空間無牆可封），純幾何路線救不到 95%，**帶著歸因證據
  回來重談目標或路線**，不硬湊、不用保留集調參充數。
- 次要護欄：配對平均 IoU 不退步（≥0.87）、過切率維持 1.0 附近、
  命名層分數不因切割變動而淨退步。

## 範圍與約束

- **只改灰階主尺**（png 管線）。`segment_rooms()` 位於
  `floorplan2dxf_color.py`、灰階彩色共用——每輪改動後彩色管線至少
  跑一次 `eval_color_walls.py` 確認不退步。
- **純幾何路線**：調 `_wall_gaps()`／`segment_rooms()`／
  `_merge_nondoor_bridges()` 的規則與參數，不引入 ML 分割。
  幾何路線碰到天花板時再回來討論是否上 ML。
- **不動 `testdata/Identify_ans/`**：答案集是人工修正過的。歸因中若
  發現答案圖本身有誤，先向使用者確認，不逕行修改。

## 量尺紀律（防過擬合）

- **開發迭代全程用 own_dataset 25 題**（`--own-dir own_dataset`）
  做歸因與 A/B 對照。
- **own_eval 保留集只在收尾驗證一次**。17 個漏切是保留集數字，
  逐案盯保留集修規則＝拿考卷練習，分數會虛胖。
- 每次規則變更以 `--report-suffix` 留 A/B 報表，僅收淨正向變更。

## 作法

### 階段一：歸因分析（先做，不先猜）

對 own_dataset 25 題跑量尺、產出逐案疊圖（`temp/eval_rooms/chk/`
機制已存在），把每個切割失誤歸入明確類別。保留集初步觀察到三種型態
（開發集分佈以歸因為準）：

1. **鄰房誤併**（floor55: 4→2、floor60: 5→3）——某開口未封，
   兩間 GT 房連成一塊
2. **過切**（floor58: 8→9、floor76: 8→10）——假封口多切出房間，
   擠掉正房配對
3. **IoU<0.5 落榜**——切出來了但形狀偏差太大（如 floor73 的 0.539）

產出：歸因表（每案：圖號、GT 房、失誤型態、具體原因、修復假設）。

### 階段二：修復迭代（每類失誤一輪）

每輪：假設 → 改規則/參數 → own_dataset A/B 對照 → 淨正向才收 →
`training/tests/` 全綠（`test_bridge_merge.py`、`test_wall_T.py` 等
已釘住既有行為）→ commit（一輪一 commit，WHY/WHAT/IMPACT）。

### 階段三：收尾驗證

1. own_eval 保留集跑一次完整管線量尺，對照 95% 目標
2. 彩色管線最終回歸
3. Readme 常駐章節與 changelog 更新（新版號）

## 不做的事（YAGNI）

- 不動命名層（DINOv2／幾何規則／限額規則）——下一輪的事
- 不引入 ML 分割模型
- 不改彩色管線的切割行為
- 不重標任何答案圖
