# RoomPilot 任務交辦範本

v1.0(2026-07-13)。給任何人(組員或 AI session)交辦工作用:**複製對應範本、填空、貼給 Claude。** 欄位不齊的任務容易做歪——特別是「允許/禁止修改範圍」與「驗收條件」,這兩欄空著的任務請先補齊再開工。

通用規則:接到任務先讀 `DEFINITION_OF_DONE.md` 對應層與 `FAILURE_LOG.md` 相關條目;宣稱完成前過一遍 `.claude/rules/verification.md`。

---

## 範本 1:實作

```text
請依 RoomPilot AI Harness 執行(先讀 DEFINITION_OF_DONE 第 N 層)。

任務:[做什麼,一句話]
動機:[為什麼要做、給誰用、產出要達成什麼——寫了這行 AI 表現明顯較好]
已知事實:[已確認的相關現況;不確定的事寫在下一欄,不要混]
不確定事項:[需要 AI 自行查證或回報的]
允許修改:[目錄/檔案清單]
禁止修改:[至少寫:其他人負責的模組、testdata、dataset、依賴版本]
輸入:[資料來源與格式]
輸出:[預期產物]
驗收條件:
1. [DoD 對應層的驗證指令與門檻,如:eval_windows ≥90/90]
2. [端到端證據,如:curl 輸出 / 截圖]
3. [pytest 全套仍通過]
回報格式:結論先行;列修改檔案;附驗證證據;未驗證的明說未驗證。
```

## 範本 2:除錯

```text
請依 RoomPilot AI Harness 除錯(先查 FAILURE_LOG 有無前例)。

症狀:[實際看到什麼,附錯誤訊息/截圖描述]
重現步驟:[指令或操作序列]
預期行為:[本來應該怎樣]
已排除的假設:[已試過什麼、為何不是它]
允許修改:[範圍]
禁止:連續疊 patch——同一假設修兩次不成就停下,重新分析根因;
     修一個症狀前先確認證據支持「這個」根因(長得像已知故障的訊號可能另有成因)。
驗收條件:
1. 說清楚根因(不是「改了就好了」)
2. 重現步驟實跑確認不再發生,附輸出
3. 對應層 DoD 驗證 + pytest 全套
4. 判斷是否值得寫入 FAILURE_LOG(升級門檻見該檔)
```

## 範本 3:審查(code review / 文件審查)

```text
請審查 [分支/diff/檔案],以 [DoD 第 N 層 / 契約 X] 為標準。

範圍:[git diff main..branch / 特定檔案]
重點:[正確性 / 介面一致性 / 單位座標系 / 入倉三規則]
規則:回報所有發現(含低嚴重度與不確定的),附信心與嚴重度,
     過濾交給我——不要自己吞掉判定低於門檻的發現。
輸出:逐條 [檔案:行號] + 問題 + 後果 + 最小修法;分 P0/P1/P2。
禁止:直接修改——先報告,修不修由我決定。
```

## 範本 4:分支整合

```text
請依 RoomPilot AI Harness 執行分支整合(先讀 DEFINITION_OF_DONE 第 7 層)。

來源分支:[名稱](歸屬確認:ancai-dev/rule/kai-dev 勿動;bella 搬資料不搬殼)
目標分支:[通常是 ben]
合併前必做:
1. git log --oneline <target>..<source> 與 git diff --stat 盤點範圍,回報給我
2. 逐條檢查入倉三規則(正本=根目錄 CLAUDE.md 的 Conventions 節)
3. 有衝突先列清單與建議解法,不要自行裁決他人模組的衝突
合併後驗收:
1. uv run pytest tests/ -v 全過
2. 受影響層的 DoD 驗證(floorplan 動了就跑 eval,server 動了就 curl)
3. git status clean,回報合併了幾個 commit、動了哪些模組
禁止:git push(整合完回報,push 由我執行)
```
