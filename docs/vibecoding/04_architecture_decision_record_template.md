# ADR-001: 向量化採正交線重建策略，不描輪廓

> **狀態:** 已接受 | **日期:** 約 2026-06（專案早期，確切日期待確認） | **決策者:** 開發團隊

## 1. 背景與問題

- **上下文**: 核心需求是把建築平面圖 PNG 轉成 AutoCAD 可用的 DXF 向量圖（公分單位，牆/窗/門）。點陣圖轉向量最直覺的做法是輪廓追蹤（contour tracing），但建築平面圖的牆體在掃描/縮放後邊緣有鋸齒與抗鋸齒灰階，直接描輪廓產出的線段會歪斜、抖動，在 CAD 中不可用。
- **問題**: 描輪廓產出的 DXF 線條不水平不垂直，牆線鋸齒化，後續的牆厚量測、窗/門符號定位、房間 flood fill 切割全都建立在乾淨的正交線之上，源頭歪了全鏈崩壞。
- **驅動因素/約束**:
  - 輸出必須是 AutoCAD 能直接編輯的乾淨線段，不是點雲式的多邊形。
  - 住宅平面圖的牆體絕大多數是水平/垂直正交結構。
  - 下游（`floorplan2room.py` 房間切割、`scripts/eval_windows.py` 評分）都假設正交幾何。

## 2. 考量的選項

### 選項一: 輪廓追蹤（cv2.findContours → approxPolyDP）
- **描述**: 對牆體二值圖抽輪廓，再用多邊形簡化逼近。
- **優點**: 實作最快；天然支援任意角度（含斜牆）。
- **缺點**: 線段歪斜（「會歪」——`scripts/README.md` 對此的原始記載）；同一面牆的兩側輪廓各自簡化後不平行，牆厚不穩定；CAD 端幾乎不可編輯。
- **成本/複雜度**: 低

### 選項二: 正交線重建（偵測線條後強制建構成純水平/垂直線）
- **描述**: 先偵測線條（含 `cv2.HoughLinesP`），再強制正交化——H 線兩端共用同一個 y、V 線兩端共用同一個 x；牆厚由平行線對距離自動偵測。實作於 `scripts/floorplan2dxf.py`（約 1400 行，參數集中在 `config.ini`）。
- **優點**: 輸出天生是乾淨的水平/垂直線段，CAD 可直接編輯；牆厚、窗/門符號、比例尺推定全部有穩定幾何基礎。
- **缺點**: 先天不支援斜線幾何——已知代價：floor24 的 2 個斜角窗永遠偵測不到（`Readme.md` 明載「正交管線（只輸出水平/垂直）先天不支援」）。
- **成本/複雜度**: 中

## 3. 決策

**選擇**: 選項二——正交線重建策略。

**理由**: 住宅平面圖以正交牆體為絕對主流，用「輸出品質的確定性」換「斜線的少數覆蓋」是划算的取捨。描輪廓的歪斜是系統性缺陷（每條線都歪），正交策略的缺陷是局部性缺陷（只有斜角元素漏失），且可事後用獨立機制補救。

## 4. 後果

- **正面**: 灰階管線最終達成牆 F1 0.99、窗 precision/recall 96%/96%（38 張灰階評分集，`Identify_ans/pngans/gray/` GT）；DXF 在 AutoCAD 中可直接編輯。彩色管線（`scripts/floorplan2dxf_color.py`）沿用同一策略。
- **負面**: 斜角窗/斜牆為永久盲區（floor24 斜角窗 ×2 為已認列漏失）；真實掃描圖的斜線填充牆也超出此策略的實心牆假設（70 張真實掃描僅 10 張可評，見 `Readme.md` 端對端盤點）。
- **影響範圍**: 兩支向量化管線、所有下游（房間切割、評測 harness、標注工具鏈）都以正交幾何為前提。
- **重新評估觸發**: 若目標圖源出現大量非正交牆體（如斜向建築、掃描圖路線 B/C 正式立項），需為斜線增設獨立偵測分支，而非推翻正交主幹。

# ADR-002: 微調 v5 權重接管預設（own 尺裁決）

> **狀態:** 已接受 | **日期:** 2026-07-25 | **決策者:** 使用者（專案負責人）裁決

## 1. 背景與問題

- **上下文**: 房型命名層使用 CubiCasa5k hourglass CNN 的語意分割做投票融合。微調 v1~v4 四輪全數未能超越官方基線權重，事後查明敗因是「牆窗門 id 失配使九成手畫標注隱形」——資料問題而非配方問題。v2.16 完成標注修復（own 尺新 GT 72 房）後，同配方微調 v5 出爐。
- **問題**: v5 在兩把量尺上結果分歧——**own 尺（own_eval 12 題）史上首勝基線**：具名命中 0.273→**0.788**（52/66）、具名 macro-F1 0.215→**0.473**，八類 recall 無一倒退（kitchen 0.4→0.9、living 0.083→1.0、bed 0.35→0.8、bath 0.43→0.86、entry 0→0.43）；但 **CubiCasa 尺未過歷屆門檻**：具名 macro-F1 0.797 < 基線 0.838（storage recall -10pp、garage recall -18pp）。是否讓 v5 接管預設權重，需人裁決。
- **驅動因素/約束**:
  - 歷屆驗收鐵律：「具名房型 recall 不得倒退」（基線具名 macro-F1 0.838，見 `docs/HANDOVER_finetune_v5.md`）。
  - 產品的實際輸入是 own 風格考卷（`png/`、`color_png/`），不是 CubiCasa 風格圖。
  - 換權重牽動 `cubicasa/room/` 的 137 個 `*_mask.npz` 語意快取與所有評測報表。

## 2. 考量的選項

### 選項一: 維持基線權重，v5 續留實驗品
- **描述**: 嚴守 0.838 門檻，CubiCasa 尺未過即不換。
- **優點**: 規則一致，CubiCasa 域表現不退。
- **缺點**: 放棄目標域（own 尺）0.273→0.788 的巨幅增益；門檻量尺與實際服務對象錯位。
- **成本/複雜度**: 低

### 選項二: v5 接管預設，門檻量尺改判給 own 尺
- **描述**: 明確定義「目標域＝own 風格」，own 尺過門檻即接管；`floorplan2room.py` 的 `CC_WEIGHTS` 指向 `model_finetuned_v5.pkl`，快取/報表/HTML 全量重算。
- **優點**: 對實際輸入的命名品質立即翻倍以上；驗收標準與產品目標對齊。
- **缺點**: CubiCasa 域 storage/garage recall 退步；門檻規則需人為改判（不能由 AI 自行放行）。
- **成本/複雜度**: 中（全量重算 137 快取＋報表）

### 選項三: 雙權重並存，按輸入域切換
- **描述**: own 圖用 v5、CubiCasa 風格圖用基線，推論前先判域。
- **優點**: 兩域都不退。
- **缺點**: 需要可靠的域判別器（不存在）；權重檔 ×2（各 200MB）；快取與評測矩陣翻倍，維運成本不成比例。
- **成本/複雜度**: 高

## 3. 決策

**選擇**: 選項二。**使用者於 2026-07-25 明確裁決：目標域＝own 風格，v5 接管預設。**

**理由**: 門檻存在的目的是保護真實服務品質；當量尺（CubiCasa 尺）與真實服務對象（own 風格考卷）錯位時，該修的是量尺不是結論。v5 首勝同時證實 v1~v4 全敗於資料層（標注 id 失配），配方本身有效，接管是對修復成果的兌現。

## 4. 後果

- **正面**: own 尺具名命中 0.788（52/66）、端對端 76.4%、配對 IoU 0.875（`json/eval_rooms/report_gtseg_ft_v5.json`、`recognition_report.html` 已同步重算）；原待辦首位「DINOv2 接融合層」降級——v5 0.788 已超 DINOv2 舊快照 0.730。
- **負面**: CubiCasa 尺 0.797（storage/garage 退步）成為已認列技術債；v5 繼承 CubiCasa5k 的 CC BY-NC 禁商用（見 ADR-003），接管預設不改變授權風險。
- **影響範圍**: `floorplan2room.py`（`CC_WEIGHTS` 預設）、`cubicasa/room/` 全量快取、`json/eval_rooms/` 報表、權重發佈機制（ADR-004）。
- **重新評估觸發**: own_dataset 擴充 50~100 題後的次輪微調（v6）出爐時；或 DINOv2 裁切分類器在新 GT 重評後反超 0.788 時。

## 5. 執行計畫（已完成）

1. 權重移至專案根 `model_finetuned_v5.pkl`，`floorplan2room.py` 預設指向之。
2. 上傳 GitHub Release tag `weights-v5`，接自動下載（ADR-004）。
3. `cubicasa/room/` 137 個 `*_mask.npz` 全量重算，報表與 `recognition_report.html` 同步。

| :--- | :--- | :--- |
| 2026-07-25 | 使用者（專案負責人） | 口頭裁決：目標域＝own，v5 接管 |

# ADR-003: 確立「去 CubiCasa」路線（CC BY-NC 授權禁商用）

> **狀態:** 已接受 | **日期:** 2026-07-23（v2.15 定案） | **決策者:** 開發團隊（授權事實驅動）

## 1. 背景與問題

- **上下文**: 房型辨識的深度學習底座是 CubiCasa5k：程式庫（`training/CubiCasa5k/floortrans/`）授權 **CC BY-NC 4.0**，Zenodo 資料集授權 **CC BY-NC-SA 4.0**。v2.15 查證實錘：官方權重與微調 v1~v5 全數繼承**禁商用**條款（與先前移除 MitUNet 同一原因）。
- **問題**: 只要商用部署，現行房型命名層整條 DL 鏈（權重＋floortrans 程式碼）都必須替換。這不是機率風險，是授權條款的確定性事實。
- **驅動因素/約束**:
  - 商用部署是專案的最終目的，授權地雷不可留。
  - 替換不能犧牲已達成的命名品質（當時語意投票基線具名正確率僅 0.270）。
  - 本機（Cody 機，WSL2）無 GPU，重訓大模型不可行；替代方案必須資料效率高、可在小樣本上成立。

## 2. 考量的選項

### 選項一: 繼續深耕 CubiCasa 微調，商用前再處理授權
- **描述**: 維持現行路線，授權問題延後。
- **優點**: 短期產出最快（v5 已證明微調有效）。
- **缺點**: 技術債持續加深——投入越多，未來替換成本越高；「商用前再處理」在時程壓力下極易變成違規上線。
- **成本/複雜度**: 低（短期）／高（長期）

### 選項二: 立即全面重寫，換授權乾淨的分割模型
- **描述**: 找 Apache/MIT 授權的平面圖分割模型從頭建置。
- **優點**: 一步到位解決授權。
- **缺點**: 無 GPU 機無法重訓；現成可商用的平面圖分割模型品質未知；會使現行 0.788 的產出線停擺。
- **成本/複雜度**: 高

### 選項三: 雙軌並行——現行線繼續出貨，同步建「房間裁切分類」替代路線
- **描述**: 把房型命名重構為「房間裁切 → 影像分類」問題：`scripts/extract_room_crops.py`（own_dataset 131 房訓練／own_eval 73 房測試）＋ `scripts/probe_room_classifier.py`（**凍結 DINOv2 ViT-S/14 骨幹＋線性頭**，8 向擴增/TTA，`--backbone` 可換）。DINOv2 為 Apache 2.0 授權，線性頭訓練 CPU 可行。長期再把 floortrans 解析自寫替換。
- **優點**: 探針已實測：具名 63 房正確率 **0.730**，勝語意投票基線 0.270 與微調 v4 的 0.619；131 張樣本即勝基線，資料效率比微調高一個量級；不停擺現行產線。
- **缺點**: 兩條線並行的維護成本；分割層（牆/窗/門 mask）的 CubiCasa 依賴仍在，需最後一哩替換（floortrans 自寫）。
- **成本/複雜度**: 中

## 3. 決策

**選擇**: 選項三——去 CubiCasa 雙軌路線。

**理由**: 授權是確定性約束，但立即斷腕會犧牲產出；DINOv2 探針用 131 張樣本就以 0.730 大勝 0.270 基線，證明替代路線技術上成立且資料效率極高，雙軌是唯一兼顧出貨與去險的走法。

## 4. 後果

- **正面**: 商用替換路徑已驗證存在（0.730 探針）；own 標注資產（`Identify_ans/own_dataset/`、`own_eval/`）同時餵養兩條路線，投資不重複。
- **負面**: v5 接管預設（ADR-002）後短期內加深 CubiCasa 依賴；「DINOv2 接進 `floorplan2room.py` 融合層」已因 v5 0.788 > 0.730（舊 GT 63 房快照）降級為「新 GT 重評後再議」；floortrans 自寫替換仍是長期未清償債務（待辦第 7 項）。
- **影響範圍**: 房型辨識管線、訓練管線、待辦優先序；商用部署 checklist 必列「權重與 floortrans 已替換」。
- **重新評估觸發**: 商用部署時程確定時（強制觸發）；DINOv2 分類器在新 GT 重評結果出爐時；own_dataset 擴充至 50~100 題後。

# ADR-004: 模型權重走 GitHub Release ＋缺檔自動下載

> **狀態:** 已接受 | **日期:** 2026-07-25 | **決策者:** 開發團隊

## 1. 背景與問題

- **上下文**: v5 接管預設後（ADR-002），`model_finetuned_v5.pkl`（200MB）成為部署必需品。GitHub 對單檔有 **100MB 硬限制**，權重無法進版控；而團隊是多機多分支協作（main/cody/bella/ben/ancai/django/kai-dev），每台機器 clone 後都需要拿到同一份權重。
- **問題**: 沒有發佈機制時，權重靠人工拷貝（隨身碟/網路傳輸），版本錯配風險高，前端/新機器 clone 後不能直接跑。
- **驅動因素/約束**:
  - GitHub 100MB 單檔硬限。
  - repo 目前為私有——下載需認證；GITHUB_TOKEN（PAT）是密碼等級秘密，依 `.claude/rules/security.md` 絕不進版控。
  - 下載品必須可驗證完整性（200MB 傳輸中斷/截斷不可靜默使用）。

## 2. 考量的選項

### 選項一: Git LFS
- **描述**: 權重用 Git LFS 追蹤，隨 clone 拉取。
- **優點**: 與 git 工作流一體，版本天然綁 commit。
- **缺點**: GitHub LFS 免費額度（儲存/頻寬各 1GB/月）對 200MB 檔的多機頻繁 clone 很快耗盡；所有成員都要裝 LFS client。
- **成本/複雜度**: 中（含持續額度成本）

### 選項二: 外部雲端儲存（雲端硬碟/物件儲存）
- **描述**: 權重放第三方儲存，README 貼連結手動下載。
- **優點**: 無容量限制。
- **缺點**: 脫離 GitHub 權限體系（要另管一套存取控制）；連結易腐化；無法程式化做完整性校驗與版本對應。
- **成本/複雜度**: 中

### 選項三: GitHub Release 資產＋程式內自動下載（採用）
- **描述**: 權重掛 Release tag [`weights-v5`](https://github.com/Tom-Yang-Ben/RoomPilot-Agent/releases/tag/weights-v5)（Release 資產單檔上限 2GB，不受 100MB 限制）。`floorplan2room.py` 內建 `_ensure_cc_weights()`：權重缺檔時自動下載，逐塊計算 **SHA-256** 比對常數 `CC_WEIGHTS_SHA256 = "b7a280d2…f4cf"`，校驗失敗即捨棄不用；私有 repo 認證讀環境變數 `GITHUB_TOKEN` / `GH_TOKEN`（或 git 憑證），repo 若轉 public 則直鏈自動生效、零設定。
- **優點**: 部署機 `clone` ＋設一個環境變數即全自動；權限沿用 GitHub 既有體系；SHA-256 保證位元級一致；版本以 Release tag 明確對應。
- **缺點**: 私有期間每台部署機都要配 PAT（秘密管理成本）；依賴 GitHub 可用性。
- **成本/複雜度**: 低

## 3. 決策

**選擇**: 選項三——GitHub Release ＋ `_ensure_cc_weights()` 自動下載。

**理由**: 唯一同時滿足「零額外服務」「沿用既有權限」「程式化完整性校驗」「clone 即可用」四項的方案；LFS 有額度天花板，外部儲存脫離權限體系。

## 4. 後果

- **正面**: 部署流程收斂為「clone → 設 `GITHUB_TOKEN` → 跑」；下載品經 SHA-256 校驗（`tests/` 有 `test_cc_weights_download` 覆蓋此路徑）；未來 v6 權重只需發新 Release tag ＋改常數。
- **負面**: PAT 是密碼等級秘密——外洩須立即輪換（`.claude/rules/security.md` 事件回應流程）；無 token 且非 public 時下載失敗，程式印出明確提示（「私有 repo 需 GITHUB_TOKEN / GH_TOKEN 或 git 憑證」）後需人工介入。
- **影響範圍**: `floorplan2room.py`（下載邏輯約於 258~373 行）、所有部署機的環境變數設定、Release 發佈 SOP。
- **重新評估觸發**: repo 轉 public（可移除 token 需求）；權重數量成長到需要獨立 model registry 時；GitHub Release 2GB 上限被逼近時。

# ADR-005: opencv-python 鎖版 `>=4.10,<5`（含 headless）

> **狀態:** 已接受 | **日期:** 2026-07（v2.16 週期，事故發生確切日期待確認） | **決策者:** 開發團隊

## 1. 背景與問題

- **上下文**: 兩支向量化管線的門偵測依賴 `cv2.HoughLinesP`。OpenCV 5.0 有破壞性變更：`HoughLinesP` 回傳 shape 從 `(N,1,4)` 改為 `(N,4)`，現有解包程式碼會當場崩潰。
- **問題**: 已發生真實事故——torch 生態安裝時拉進 `opencv-python-headless` 5.0.0，**後裝者蓋掉 cv2 模組**，把既有的 opencv-python 4.13 覆蓋，兩支管線的門偵測直接掛掉（`Readme.md` v2.16 記載：「本次事故：headless 5.0.0 蓋掉 4.13」）。
- **驅動因素/約束**:
  - `opencv-python` 與 `opencv-python-headless` 是同名模組 `cv2` 的兩個發行包，pip 不視為衝突，**後安裝者靜默覆蓋**——鎖一顆不夠。
  - `.claude/rules/security.md` 要求提交 lock file / 明確依賴管理。
  - `.venv` 重建（`pip install -r requirements.txt`）必須可重現。

## 2. 考量的選項

### 選項一: 改程式碼相容兩種 shape
- **描述**: 所有 `HoughLinesP` 呼叫點加 shape 正規化（`reshape(-1, 4)`）。
- **優點**: 不受版本擺佈，未來升 5.x 免改。
- **缺點**: `scripts/floorplan2dxf.py` 已凍結（ADR-006），依鐵律不得修改；且 5.0 的破壞性變更未必只有這一處，逐點相容是打地鼠。
- **成本/複雜度**: 中

### 選項二: requirements.txt 雙包鎖版 `<5`（採用）
- **描述**: `requirements.txt` 同時鎖兩顆：`opencv-python>=4.10,<5` 與 `opencv-python-headless<5`，各附註解說明原因（第 2~3 行）。
- **優點**: 一行解決；凍結檔零接觸；headless 覆蓋路徑也被擋住；註解讓後人不會誤解鎖版理由而貿然解鎖。
- **缺點**: 長期擋在 4.x，未來若需要 5.x 新功能須先做完整相容遷移。
- **成本/複雜度**: 低

## 3. 決策

**選擇**: 選項二——`requirements.txt` 雙包鎖 `<5`。

**理由**: 凍結鐵律排除了改程式碼的路（選項一違反 ADR-006）；鎖版是唯一同時保護凍結管線與彩色管線、且對 headless 靜默覆蓋路徑也有效的做法。關鍵洞察是**必須兩顆都鎖**——只鎖 `opencv-python` 時，torch 生態拉進的 headless 5.0 仍會後裝覆蓋。

## 4. 後果

- **正面**: `.venv` 重建可重現；本次事故類型（headless 蓋版）被結構性阻斷；門偵測（灰階過濾率 100%、門位 fused P 0.576/R 0.868）不再受上游波動。
- **負面**: 停留 4.x 是有意識的技術債；任何新依賴若硬性要求 opencv 5 會直接衝突（安裝時即報錯，屬可接受的快速失敗）。
- **影響範圍**: `requirements.txt`、兩支向量化管線、所有機器的 `.venv` 重建流程。
- **重新評估觸發**: 灰階管線解凍（不可能，見 ADR-006）或彩色管線確有 5.x 必要功能時——屆時先做全呼叫點 shape 相容再解鎖。

# ADR-006: 灰階管線凍結，開發只走彩色管線

> **狀態:** 已接受 | **日期:** 約 2026-07（彩色管線成為開發主力時，確切日期待確認） | **決策者:** 使用者＋開發團隊

## 1. 背景與問題

- **上下文**: 灰階向量化管線 `scripts/floorplan2dxf.py`（約 1400 行）已達到極高水準：灰牆 F1 0.99、灰窗 precision/recall 96%/96%（38 張評分集）。開發重心轉向彩色平面圖（`color_png/` 29 題），彩色管線 `scripts/floorplan2dxf_color.py`（約 1900 行）成為主力，現況彩牆 87.7/94.9、**彩窗 P62/R38 為全系統最低**。
- **問題**: 兩支管線共享大量演算法概念，改彩色時「順手也修灰階」的誘惑極高；但灰階已近天花板，任何改動的期望值為負——歷史上曾有 density-based 窗偵測重寫因大量誤報而整體回退（記錄於專案記憶）。每次意外退化都要靠評分集抓回，成本高昂。
- **驅動因素/約束**:
  - 灰階 0.99/96% 幾乎無上升空間，風險/報酬完全不對稱。
  - 評測鐵律：改 chk/dxf 邏輯前必先跑 `scripts/eval_windows.py` 對 `Identify_ans/pngans/` 評分，不得退化後覆蓋。
  - 彩窗召回 38% 是最大真實破口，開發火力必須集中。

## 2. 考量的選項

### 選項一: 單一管線＋色彩模式開關
- **描述**: 合併為一支程式，用參數切換灰階/彩色行為。
- **優點**: 演算法改進兩邊共享，無重複碼。
- **缺點**: 彩色的每次調參/重構都讓灰階回歸測試變成必要成本；共用碼路徑使「彩色實驗」與「灰階穩定」在物理上不可隔離；0.99 的資產暴露在每日開發風險下。
- **成本/複雜度**: 高（持續回歸成本）

### 選項二: 灰階整檔凍結，彩色獨立檔獨立配置（採用）
- **描述**: `floorplan2dxf.py` ＋ `config.ini` 明文凍結（`scripts/README.md`：「**此檔已凍結，不再修改**」）；開發只動 `floorplan2dxf_color.py` ＋ `config_color.ini`。輸出目錄完全隔離：彩色進 `training/chk/color/`、`dxf_scale/color/`、`json/color/`，灰階在 `training/chk/gray/`、`dxf_scale/gray/`、`json/gray/`，互不覆蓋。灰階若真需要新能力，以「凍結檔零接觸」的後處理腳本外掛（先例：門位融合四支腳本只讀寫 `json/gray/`，把門位從 P 0.361/R 0.132 提升到 P 0.588/R 0.858，主管線一行未動）。
- **優點**: 0.99 資產被制度性保護；彩色開發零心智負擔（怎麼改都不會弄壞灰階）；後處理外掛模式證明凍結不等於停止進步。
- **缺點**: 兩檔間演算法概念重複（正交策略、牆厚偵測各有一份）；彩色端的通用改進無法回饋灰階。
- **成本/複雜度**: 低

## 3. 決策

**選擇**: 選項二——灰階整檔凍結，開發只走彩色管線。

**理由**: 灰階已在天花板，任何共享機制帶來的「改進回饋」期望值趨近零，而「意外退化」的風險真實存在（density 重寫事故為證）。凍結＋輸出隔離＋後處理外掛，用最低成本同時取得穩定與演進空間。此決策已固化為專案記憶：「只改 floorplan2dxf_color.py，floorplan2dxf.py 凍結不動」。

## 4. 後果

- **正面**: 灰階 0.99/96% 自凍結以來零退化；彩色管線快速迭代（v2.16 彩牆 87.7/94.9、IoU 83.8）；門位融合以外掛完成而未觸凍結檔。
- **負面**: 雙份演算法碼的維護分裂；彩窗召回 38% 只能在彩色檔內解（調參方向：牆段配對 gap 與 covered 門檻的線寬適配）；凍結檔內若發現潛在 bug（如 HoughLinesP shape 問題）只能從外圍防禦（ADR-005 的鎖版即是）。
- **影響範圍**: `scripts/floorplan2dxf.py`（禁改）、`scripts/floorplan2dxf_color.py`（唯一開發面）、輸出目錄結構、後處理腳本設計原則（只讀寫 json，零接觸主管線）。
- **重新評估觸發**: 彩色管線品質全面追平灰階、且出現必須雙管線共享的重大架構演進時；或灰階評分集擴充後暴露出 0.99 以外的系統性缺陷時。
