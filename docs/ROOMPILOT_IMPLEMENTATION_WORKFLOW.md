# RoomPilot 專題實施流程

最後更新：2026-07-10

> 本版新增決策：3D 生成頁以「聊天式 AI 訪談」取代大量選項；需求確認後必須輸出可保存、可回放的 JSON。風格提案先使用地端預製的配色圖卡與室內情境圖，再將確認結果套用至 GLB 場景。

## 文件目的

本文件整理 RoomPilot 在「提案與溝通階段」的實際實施流程，聚焦於以下五個核心階段：

1. Program 需求訪談
2. 2D 配置轉 3D 白模 / 骨架
3. 風格與材質提案
4. 3D 提案畫面 / 渲染
5. 互動微調

這份文件的目的不是描述傳統室內設計公司的全流程，而是定義 RoomPilot 這個專題在現階段真正要落地的系統流程、資料流與實作重點。

---

## 專題主線

RoomPilot 的核心不是「直接生成漂亮圖片」，而是把室內設計前期提案流程數位化，形成可互動、可驗證、可迭代的空間提案系統。

系統主線應為：

`需求收集 -> 空間確認 -> 平面配置 -> 3D 白模 -> 風格提案 -> 渲染呈現 -> 互動微調 -> 輸出結果`

其中最重要的原則是：

- 先確認空間與配置，再談風格
- 先確認骨架與比例，再做渲染
- 互動微調是系統價值，不是附屬功能

## 2026-07-10 新版使用者流程與 JSON 契約

### 新版主線

3D 生成頁不再以大量下拉選單或勾選項目作為主要入口，改成固定節奏的聊天式 AI 訪談：

`聊天訪談 -> client_brief JSON -> 使用者確認 -> 地端風格圖卡 -> 風格方案確認 -> 3D 白模與 GLB 場景 -> 材質/色彩微調 -> 隱藏天花板與吊燈觀看 -> 室內行走模式`

聊天介面仍須使用結構化欄位收斂答案，避免自由對話造成資料缺漏。AI 每次只問一個問題；必要欄位完成後顯示需求摘要，使用者確認前不得直接生成場景。

### `client_brief` 最小輸出格式

需求確認時，前端與後端都以同一份 JSON 作為資料契約。完整格式見 `docs/client_brief.schema.json`。

```json
{
  "schema_version": "1.0",
  "created_at": "2026-07-10T00:00:00Z",
  "space": {
    "type": "living_room",
    "width_cm": 420,
    "depth_cm": 360,
    "floorplan_filename": null
  },
  "occupants": {"adults": 2, "children": 0, "elderly": 0, "pets": 0},
  "needs": ["storage", "entertaining"],
  "style": {
    "preferred": ["japanese"],
    "colors": ["warm_neutral"],
    "materials": ["wood", "fabric"],
    "selected_card_id": null
  },
  "constraints": ["keep_window_clear", "keep_door_clear"],
  "notes": "",
  "confirmation": {"status": "draft", "confirmed_at": null}
}
```

### 地端風格提案

每一種風格先準備 3 到 4 組地端方案卡，每張卡包含 `card_id`、色票、牆面、地板、家具材質、情境圖與推薦說明。使用者選定並確認後，才將 `selected_card_id` 寫回 `client_brief`，並套用到 3D 場景。

### 3D 場景設定

- 牆面與地板沿用 `surface_catalog` 即時切換。
- GLB 優先支援同款不同色/材質 variant；沒有 variant 時才使用整件 tint。
- 天花板、吊燈與燈光分開管理；隱藏天花板不得移除吊燈或光源。
- 編輯模式負責拖曳、旋轉、材質切換；行走模式負責第一人稱室內觀看，並以碰撞檢查避免穿牆或穿家具。

### JSON 驗收標準

- 每次完成訪談都能顯示並下載 `client_brief.json`。
- 送出生成 API 的 payload 必須包含 `client_brief`，不得只依賴散落的表單欄位。
- 使用者未確認需求或風格方案時，不能進入正式 3D 生成。
- 重新整理頁面後，仍可從 JSON 還原需求摘要與已選方案。

## 1. Program 需求訪談

### 目的

把使用者模糊的生活需求，轉成系統可理解、可計算、可作為配置與風格推薦依據的結構化條件。

### 這一步要解決的問題

- 使用者常常只會說「想要溫暖一點」、「想要收納多一點」
- 如果沒有先整理成規則，後續家具配置與風格提案都會失焦
- 系統不能直接依賴一句自然語言就決定整個空間方案

### 應收集的資訊

#### 空間基本資訊

- 空間類型：客廳、臥室、書房、餐廳、多功能空間
- 使用人數
- 家庭成員：成人、小孩、長輩、寵物

#### 生活機能需求

- 收納需求高 / 中 / 低
- 是否需要工作區
- 是否需要閱讀區
- 是否需要展示區
- 是否重視接待或聚會
- 是否需要寬動線或無障礙

#### 風格與材質偏好

- 偏好風格：北歐、日式、現代、奶油風、工業風、美式等
- 喜歡的色彩方向：淺色、深色、暖色、冷色、中性色
- 喜歡的材質方向：木質、石材、布料、金屬、玻璃

#### 預算與限制

- 預算區間
- 是否偏好現成家具
- 是否接受客製櫃體
- 是否有不可更動的門、窗、牆、設備

### 實施步驟

1. 先用表單式流程收集關鍵需求，避免一開始完全自由對話造成資訊散亂。
2. 將使用者回答整理為標準化 `client_brief`。
3. 將 `client_brief` 轉成系統規則，例如收納優先度、動線需求、家具優先順序與風格權重。
4. 在進入配置前顯示「需求摘要」讓使用者再次確認。

### 建議輸出格式

```json
{
  "space_type": "bedroom",
  "occupants": {
    "adults": 2,
    "children": 0,
    "elderly": 1,
    "pets": 0
  },
  "functional_needs": ["high_storage", "reading_corner"],
  "style_preferences": ["japandi", "modern"],
  "material_preferences": ["wood", "fabric"],
  "color_preferences": ["warm_neutral"],
  "budget_level": "medium",
  "constraints": ["keep_wide_walkway"]
}
```

### 驗收標準

- 需求能被統一整理成固定格式
- 配置模組與風格模組都能讀取這份資料
- 使用者能在生成前確認摘要內容

## 2. 2D 配置轉 3D 白模 / 骨架

### 目的

讓使用者先確認空間比例、格局、家具大小與動線是否合理，而不是直接跳到漂亮渲染圖。

### 這一步要解決的問題

- 只有 2D 配置時，使用者很難想像空間感
- 如果一開始就渲染，容易掩蓋比例錯誤與動線問題
- 沒有白模階段，使用者會把「風格不好看」跟「空間規劃有問題」混在一起

### 輸入資料

- 房間輪廓資料
- 牆、門、窗與開口資料
- 家具配置結果
- 家具尺寸與模型資料

### 實施步驟

1. 將 2D 房間幾何資料轉成 3D 房間白模。
2. 建立地板、牆體、門洞、窗洞等基礎空間骨架。
3. 將已配置家具以正確尺寸、位置、旋轉角度放入場景。
4. 提供至少四組固定視角：
   - 俯視
   - 入口視角
   - 角落視角
   - 室內視角
5. 加入基本互動：
   - 旋轉
   - 縮放
   - 家具選取
   - 占地框與比例檢查

### 工程重點

- 3D 白模的重點是「對」，不是「漂亮」
- 家具位置與 2D 配置必須一致
- 座標系、單位、公尺與公分轉換要完全統一
- 固定視角比自由亂轉更適合溝通與比對

### 驗收標準

- 房間輪廓與牆體正確
- 家具比例正確
- 使用者可看懂空間結構與動線
- 白模可作為後續風格提案的骨架

## 3. 風格與材質提案

### 目的

在空間骨架與家具配置成立後，由系統像設計師一樣給出可落地的風格方向，而不是讓使用者自行亂選大量元素。

### 這一步要解決的問題

- 使用者通常不知道不同風格背後的材質與色彩邏輯
- 若讓使用者自由混搭，結果容易失控
- 風格若沒有建立在空間條件上，只會變成貼皮

### 風格提案應包含的內容

- 風格名稱
- 主色、輔色、點綴色
- 牆面建議
- 地板建議
- 家具材質建議
- 推薦原因
- 不建議元素

### 實施步驟

1. 讀取 `client_brief`、空間類型、家具配置與房間條件。
2. 從風格資料庫中篩出適合的候選風格。
3. 根據空間條件與生活需求做排序，例如：
   - 小空間提高淺色低壓迫風格權重
   - 高收納需求提高整合式風格權重
   - 長輩使用降低動線複雜的方案權重
4. 只輸出 2 到 3 組推薦方案，避免選項爆炸。
5. 讓使用者套用其中一組方案到場景。
6. 套用後同步更新：
   - 牆面
   - 地板
   - 家具候選風格
   - 後續渲染設定

### UI 呈現建議

每組方案至少顯示：

- 風格縮圖
- 色票列
- 材質卡片
- 簡短推薦理由
- 套用按鈕

### 驗收標準

- 系統能提出收斂後的方案，而非無限制選項
- 套用後能明顯反映在場景中
- 使用者能理解推薦理由

## 4. 3D 提案畫面 / 渲染

### 目的

在空間、配置與風格都穩定之後，產出更接近提案成品的畫面，用於理解氛圍、做方案說服與正式展示。

### 這一步要解決的問題

- 白模能確認結構，但不能完整傳達最終氛圍
- 客戶需要更直觀的視覺效果來理解材質與風格
- 渲染圖若沒有結構依據，會變成不可信的美圖

### 前提條件

進入渲染前必須先鎖定：

- 房間幾何
- 家具配置
- 風格方案
- 牆地材質
- 視角

### 實施步驟

1. 產出一份完整的渲染條件包。
2. 固定幾個展示視角，避免每次輸出結果差異過大。
3. 先做 P0 版本：
   - 3D viewer 材質套用
   - 固定視角截圖
4. 若進一步做 AI 渲染：
   - 保持空間結構不變
   - 將白模、材質與風格條件作為渲染依據
5. 輸出結果可包含：
   - 主視角效果圖
   - 多視角比較圖
   - before / after 對照圖

### 工程重點

- 視角必須可重現
- 渲染輸入要可記錄、可回放
- 不能為了好看而破壞空間結構

### 驗收標準

- 渲染結果與白模、配置一致
- 風格差異清楚可辨
- 可用於簡報、提案與展示

## 5. 互動微調

### 目的

把真實設計過程中的多輪討論，轉化成系統中的即時操作與即時驗證。

### 這一步要解決的問題

- 真實設計不可能一次到位
- 使用者一定會想改位置、換家具、換材質、換風格
- 如果每次修改都要重新整套生成，體驗會很差

### 支援的操作類型

#### 家具微調

- 拖曳位置
- 旋轉角度
- 前後左右微移
- 替換同類家具
- 新增家具
- 刪除家具

#### 風格微調

- 更換風格方案
- 更換牆面材質
- 更換地板材質
- 局部更換家具材質或色系

### 實施步驟

1. 使用者在 3D viewer 中選取家具或材質區域。
2. 系統提供直接操作或快捷控制。
3. 每次操作後即時進行合法性驗證：
   - 是否撞牆
   - 是否重疊
   - 是否堵門
   - 是否超出房間範圍
   - 是否違反基本淨空規則
4. 若合法，更新場景資料。
5. 若不合法，顯示原因並阻止或警告。
6. 保存版本紀錄，支援回復前一步。

### UI 建議

微調至少要同時支援兩種方式：

- 直接操作：拖曳、旋轉、控制鈕
- 語意操作：例如「往左移 20 公分」、「換成木質床頭櫃」

第一版建議先把直接操作做穩，再補語意微調。

### 驗收標準

- 使用者可以立即看到修改結果
- 不合法操作會被即時處理
- 微調結果能同步回白模、風格與後續輸出

## 建議整體實施順序

如果依開發風險與價值排序，建議優先順序如下：

1. 先把 Program 需求訪談結構化
2. 再把 2D 配置與 3D 白模串穩
3. 接著做風格與材質推薦
4. 再補提案畫面與渲染
5. 最後補強互動微調閉環

這樣的原因是：

- 沒有需求資料，系統不知道該怎麼配置
- 沒有白模骨架，風格只是貼皮
- 沒有風格收斂，渲染只是亂生圖
- 沒有互動微調，系統就少了 RoomPilot 最有價值的差異化

---

## 最終流程摘要

RoomPilot 的正確流程不是：

`輸入需求 -> 直接出圖`

而是：

`需求訪談 -> 空間確認 -> 家具配置 -> 3D 白模 -> 風格材質提案 -> 渲染呈現 -> 互動微調 -> 輸出成果`

這樣才符合真實設計邏輯，也才是你們專題與一般 AI 生圖工具真正的差異。

## 現有 GLB 家具如何做到換顏色與材質

這一段是現階段最需要講清楚的工程決策。

先講結論：

### 現況可以做到什麼

以你們目前的 GLB 家具與 viewer 架構，可以做到：

1. **牆面與地板材質切換**
   - 已經做到
   - 由 `scene.js` + `scene_viewer.js` + `surface_catalog.json` 驅動

2. **家具整件替換**
   - 已經可以做到基礎版本
   - 例如同類型家具換另一件不同風格的 GLB

3. **家具材質顏色 runtime 覆蓋**
   - 技術上可做
   - 但目前 repo 還沒有正式實作

### 現況不能直接保證做到什麼

1. **所有 GLB 都能精準局部換材質**
   - 不保證
   - 因為不同 GLB 的 mesh 結構、material 命名、貼圖方式不一致

2. **用單一規則把所有家具任意換皮**
   - 不現實
   - 尤其來自不同來源的 GLB，材質切法不一致

---

## 三種可行方案

### 方案 A：整件家具換色調 Tint

#### 做法

GLB 載入後，遍歷 `mesh.material`，對可染色材質套用：

- `material.color`
- 必要時保留原本 `map`
- 用乘色方式做整體色調偏移

#### 優點

- 最快落地
- 不需要重做 GLB
- 適合布沙發、木頭、單色烤漆家具

#### 缺點

- 如果原本貼圖很複雜，效果有限
- 無法精準只改某一部分
- 金屬、玻璃、複合材質效果可能不自然

#### 適合用途

- 奶油白、淺灰、深胡桃、黑色等「同材質不同色調」

#### 工程建議

在 `scene_viewer.js` 的 `loader.loadAsync(item.model_url)` 後面加一層：

- 根據 `item.material_override` 或 `item.color_override`
- 遍歷 mesh
- 對可染色 material 套 `color`

---

### 方案 B：按材質槽位局部替換

#### 做法

前提是 GLB 裡的 material slot 或 mesh name 有規律，例如：

- `fabric`
- `wood`
- `metal`
- `glass`

載入後只替換特定材質：

- 木頭部分換木紋 texture
- 布面部分換布料顏色
- 金屬部分換黃銅 / 黑鐵

#### 優點

- 比整件 tint 更專業
- 可做到「木腳不變、布面換色」

#### 缺點

- 需要 GLB 資產結構夠乾淨
- 不同來源家具可能命名不一致
- 前期要建立 mapping 規則

#### 適合用途

- 沙發布面換色
- 木腳 / 金屬腳切換
- 櫃體門片與把手分材質

#### 工程建議

建立一份 furniture material profile，例如：

```json
{
  "furniture_id": "sofa_001",
  "material_slots": {
    "fabric": ["Fabric", "Seat", "Cushion"],
    "wood": ["Leg", "Wood", "Frame"],
    "metal": ["Metal", "Handle"]
  }
}
```

viewer 載入後依這份 profile 定位對應 mesh / material 做替換。

---

### 方案 C：直接換不同顏色版本的 GLB

#### 做法

如果資料庫裡本來就有：

- 白色版
- 黑色版
- 胡桃木版
- 米色版

那最穩的方式其實不是改材質，而是**直接替換成另一個 GLB**。

#### 優點

- 最穩定
- 視覺最自然
- 不會因 runtime 染色導致質感跑掉

#### 缺點

- 要有足夠多的顏色版本資產
- 需要 catalog 做 variant 關聯

#### 適合用途

- IKEA 同款不同色
- 明確已有色號版本的家具

#### 工程建議

在 merged catalog 裡補：

- `variant_group_id`
- `variant_color`
- `variant_material`

讓前端可以在「同款不同色」之間切換，而不是硬染。

## 我最建議你們的實作策略

如果以目前 repo、時間與資產現況來看，最實際的做法是：

### 第一階段

- 牆面 / 地板維持現在的材質切換流程
- 家具先做「同款不同 GLB 版本替換」
- 若沒有 variant，就做整件 tint

### 第二階段

- 挑少數主力家具類型做局部材質替換
  - 沙發
  - 床
  - 餐椅
  - 櫃體

### 第三階段

- 為常用家具建立 material slot profile
- 形成真正的「布面、木腳、金屬件」分開換材質能力

## 實務判斷

如果你們現在是為了專題 demo 成功率，我的建議很明確：

- **不要一開始就追求所有 GLB 任意換材質**
- 先做：
  - 牆地材質完整切換
  - 家具同款 variant 切換
  - 少量家具整體 tint

因為這三件事最有機會在短時間內做出「使用者看得懂、老師也看得出差異」的成果。

真正高精度的局部材質替換，應該只挑少數高價值家具類型做 showcase，而不是要求整個 10,000+ GLB 資料庫全部支援。
