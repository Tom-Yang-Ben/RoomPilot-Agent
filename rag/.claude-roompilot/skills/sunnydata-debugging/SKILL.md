# 系統化除錯（RoomPilot）

## 總覽

亂改一通浪費時間、還會製造新 bug。快速補丁只會蓋住底層問題
（例如檢索回 0 筆就把 `where` 整段拿掉——結果永遠不知道是 `rag_indexable` 寫錯了地方）。

**核心原則：** 一律先找到根因，才動手修。修症狀就是失敗。

**違反這套流程的字面規定，就是違反除錯的精神。**

## 鐵律

```
沒有先做根因調查，就不准提出修法
```

沒完成 Phase 1，你就不能提出修法。

## 何時使用

任何技術問題都用：
- 測試失敗（本專案 pytest **尚未建置**，等同「CLI 實查結果不符預期」）
- 上線後的 bug（本專案 = Demo／實機執行時出錯）
- 非預期行為（檢索結果與需求明顯不搭）
- 效能問題（單次查詢等太久、rerank 拖到十幾秒）
- 建置失敗（`embed_v3.py` 建索引中途炸掉）
- 整合問題（`query_parser` 輸出的欄位在 `retriever` 這端對不上）

**以下情境「特別」要用：**
- 有時間壓力時（趕 Demo 最容易讓人想用猜的）
- 「只改這一行就好」看起來很明顯時
- 你已經試過好幾種修法
- 上一個修法沒有用
- 你其實沒完全弄懂這個問題

**不准跳過的情況：**
- 問題看起來很簡單（簡單的 bug 也有根因）
- 你在趕時間（趕出來的東西保證要重做）
- 有人要你「現在馬上」修好（系統化比亂試快）

## 四個階段

你**必須**完成每個階段才能進入下一個。

### Phase 1：根因調查

**動手做「任何」修改之前：**

1. **仔細讀錯誤訊息**
   - 不要跳過錯誤或警告
   - 它們常常直接寫著答案（例如 `structured outputs` 的 400 會指出是哪個 property 的 schema 不合法）
   - 完整讀 traceback
   - 記下行號、檔案路徑、錯誤碼（Anthropic API 的 `400 invalid_request_error`、Chroma 的 `where` 驗證錯誤）

2. **穩定重現**
   - 你能可靠地觸發它嗎？
   - 精確步驟是什麼？（把觸發查詢寫下來，例如 `.venv-rag/bin/python rag_pipeline/retriever.py "工業風、預算三萬的書房書桌"`）
   - 每次都會發生嗎？（rerank 分數異常常常只在特定類別出現）
   - 無法重現 → 蒐集更多資料，不要用猜的

3. **檢查最近的改動**
   - 有什麼改動可能造成這個？
   - 專案**尚未 git init**，沒有 `git diff` 可用；改以：檔案修改時間（`ls -lt rag_pipeline/`）、
     `docs/` 與程式是否脫鉤、`chroma_db/` 與 `rag_dataset/furniture_enriched_v3.json` 的時間先後
   - 新裝的套件、設定改動（`category_groups.json`、`taxonomy_v2.json` 有沒有被動過）
   - 環境差異（`HF_HUB_OFFLINE`、`ANTHROPIC_API_KEY` 是否存在、device 落在 MPS 還是 CPU）

4. **在多元件系統中蒐集證據**

   **當系統有多個元件時**（本專案：需求解析 → 硬過濾 → 向量檢索 → rerank → 加權收斂 → UI 呈現）：

   **提出修法之前，先加診斷探針：**
   ```
   對每一個元件邊界：
     - 記錄進入該元件的資料
     - 記錄離開該元件的資料
     - 確認環境／設定有正確傳遞下去
     - 檢查每一層的狀態

   先跑一次，蒐集能顯示「在哪裡壞掉」的證據
   然後分析證據，找出失效的元件
   然後才去調查那個特定元件
   ```

   **範例（RoomPilot 多層管線；症狀：UI 卡片空白、檢索回 0 筆）：**
   ```bash
   PY=.venv-rag/bin/python

   # 第 1 層：環境與金鑰
   echo "=== 環境 ==="
   [ -f .anthropic_key ] && echo "KEY: SET" || echo "KEY: UNSET"
   echo "HF_HUB_OFFLINE=${HF_HUB_OFFLINE:-未設(程式內會 setdefault=1)}"

   # 第 2 層：需求解析輸出（受控詞彙是否正確）
   echo "=== query_parser 輸出 ==="
   $PY rag_pipeline/query_parser.py "日式侘寂感、預算兩萬內的客廳沙發"

   # 第 3 層：Chroma 硬過濾條件與命中數
   echo "=== 索引本身還在嗎 ==="
   $PY -c "import chromadb; c=chromadb.PersistentClient('chroma_db').get_collection('furniture_v3'); print('count=', c.count())"

   # 第 4 層：完整檢索（會印出 where 與各階段筆數）
   echo "=== retriever 全流程 ==="
   $PY rag_pipeline/retriever.py "日式侘寂感、預算兩萬內的客廳沙發"
   ```

   **這會揭露：** 是哪一層壞掉（金鑰 → 解析 ✓、解析 → `where` ✗，例如 `where` 混進了
   `rag_indexable` 這個不在 `chroma_metadata` 裡的頂層欄位，於是必然命中 0 筆）

5. **追蹤資料流**

   **當錯誤出現在呼叫堆疊深處時：**

   完整的反向追蹤技術見本目錄的 `root-cause-tracing.md`。

   **速記版：**
   - 這個壞值是從哪裡產生的？
   - 是誰帶著這個壞值呼叫進來的？
   - 一路往上追，直到找到源頭
   - 修在源頭，不要修在症狀點

### Phase 2：模式分析

**修之前先找出模式：**

1. **找出可運作的範例**
   - 在同一個程式庫裡找類似但正常運作的程式碼
   - 什麼東西跟壞掉的很像、但它是好的？（例如「沙發」查詢正常、「地毯」查詢回 0 筆——差別在哪？）

2. **對照參考實作**
   - 若要套用某個模式，把參考實作**完整**讀過
   - 不要略讀——每一行都讀（`build_where()` 的 clauses 組法、`nullable()` 為何用 `anyOf`，程式註解裡都寫了原因）
   - 完全理解該模式後才套用

3. **找出差異**
   - 正常的跟壞掉的之間，有什麼不同？
   - 把每一個差異都列出來，再小也列（`role`、`size_class`、`category_group` 任一個對不上都會清空結果）
   - 不要預設「那個不可能有影響」

4. **理解依賴**
   - 這個東西還需要哪些元件？（`taxonomy_v2.json`、`category_groups.json`、`chroma_db/`、兩個 HF 模型）
   - 需要哪些設定、組態、環境？（`HF_HUB_OFFLINE`、device=MPS/CPU、記憶體約 4.6 GB 常駐）
   - 它做了哪些假設？（例如假設 metadata 欄位存在、假設 reranker 輸出已是 0–1）

### Phase 3：假設與測試

**科學方法：**

1. **形成單一假設**
   - 清楚陳述：「我認為 X 是根因，因為 Y」
     （例：「我認為根因是 `where` 帶了 `rag_indexable`，因為把它拿掉後同一查詢由 0 筆變 37 筆」）
   - 寫下來
   - 要具體，不要含糊

2. **最小化測試**
   - 為了驗證假設，做**最小**的改動
   - 一次只動一個變數
   - 不要一次修好幾個東西

3. **確認後再往下**
   - 有效嗎？有 → Phase 4
   - 無效？形成**新的**假設
   - **不要**在舊修法上疊新修法

4. **當你不知道時**
   - 直接說「我不理解 X」
   - 不要假裝懂
   - 求助
   - 再多查資料（本專案先查 `docs/RAG檢索系統說明.md`、`docs/query_parser_spec.md`）

### Phase 4：實作

**修根因，不修症狀：**

1. **建立會失敗的測試案例**
   - 最簡單的重現方式
   - 能自動化就自動化
   - 沒有測試框架時，寫一次性測試腳本
     （本專案 pytest **尚未建置**，現階段就是寫 `scripts/repro_xxx.py` 或一行 `.venv-rag/bin/python -c "..."`）
   - 修之前**必須**先有它
   - 寫正確的失敗測試請用 `sunnydata-testing` skill

2. **實作單一修法**
   - 針對已確認的根因
   - 一次一個改動
   - 不要順手做「反正我人都在這了」的改良
   - 不要夾帶重構

3. **驗證修法**
   - 測試現在通過了嗎？（或：那句查詢現在回得出合理的 8 張卡片了嗎？）
   - 有沒有弄壞其他東西？（拿另外 3 句不同房型／風格的查詢回歸一次）
   - 問題真的解決了嗎？

4. **如果修法沒用**
   - 停
   - 數一數：你已經試過幾種修法？
   - 若 < 3：回到 Phase 1，帶著新資訊重新分析
   - **若 ≥ 3：停下來質疑架構（下面第 5 點）**
   - 沒有先做架構層面的討論，**不要**嘗試第 4 個修法

5. **若 3 次以上修法都失敗：質疑架構**

   **代表架構有問題的徵兆：**
   - 每個修法都在不同地方翻出新的共用狀態／耦合／問題
     （例如：為了讓結果不為 0，硬過濾條件一個一個被拔掉，最後檢索退化成全庫語意搜尋）
   - 修法需要「大規模重構」才做得出來
   - 每個修法都在別處製造新症狀

   **停下來質疑根本假設：**
   - 這個模式從根本上是對的嗎？（風格到底該硬過濾還是軟加權？）
   - 我們是不是「純粹因為慣性才繼續沿用」？
   - 該重構架構，還是繼續修症狀？

   **在嘗試更多修法之前，先跟你的人類夥伴討論**

   這不是假設失敗——這是架構選錯了。

## 紅旗警訊 — 停下來，照流程走

如果你發現自己在想：
- 「先快速修一下，之後再調查」
- 「先改改看 X，看會不會好」
- 「一次改好幾個地方，再一起跑跑看」
- 「測試就跳過吧，我手動確認一下就好」
- 「大概是 X 吧，我來改」
- 「我沒完全懂，但這樣改應該會動」
- 「參考做法是 X，但我照自己的方式改一下」
- 「主要問題有這些：[沒調查就列出一堆修法]」
- 還沒追資料流就先提出解法
- **「再試最後一個修法」（已經試過 2 次以上時）**
- **每個修法都在不同地方翻出新問題**

**以上全部都代表：停。回到 Phase 1。**

**若 3 次以上修法都失敗：** 質疑架構（見 Phase 4 第 5 點）

## 人類夥伴發出的「你做錯了」訊號

**留意這些導正：**
- 「那件事沒發生嗎？」— 你沒驗證就假設了
- 「這樣會顯示出……嗎？」— 你應該先加證據蒐集
- 「別再猜了」— 你在還沒理解時就提修法
- 「深入想一下這件事」— 要質疑根本假設，不是只看症狀
- 「我們卡住了？」（帶著挫折）— 你的做法沒有用

**看到這些時：** 停。回到 Phase 1。

## 常見的自我合理化

| 藉口 | 現實 |
|--------|---------|
| 「問題很簡單，不需要走流程」 | 簡單問題也有根因。流程對簡單 bug 反而很快。 |
| 「緊急狀況，沒時間走流程」 | 系統化除錯比亂猜亂試**更快**。 |
| 「先試這個，之後再調查」 | 第一個修法會定調。一開始就做對。 |
| 「等確認修法有效再補測試」 | 沒測試的修法留不住。先測才能證明。 |
| 「一次修多個比較省時間」 | 分不出是哪個有效，還會製造新 bug。 |
| 「參考文件太長，我直接改一改套用」 | 一知半解保證出 bug。完整讀完它。 |
| 「我看到問題了，我來修」 | 看到症狀 ≠ 理解根因。 |
| 「再試一個修法就好」（已失敗 2 次以上） | 3 次以上失敗 = 架構問題。質疑模式，不要再修。 |
| 「rerank 分數怪怪的，再套一層 sigmoid 壓一下就正常了」 | `bge-reranker-v2-m3` 經 CrossEncoder 已輸出 0–1，再套會壓縮區分度。這是修症狀。 |
| 「檢索回 0 筆，把 `where` 拿掉就有結果了」 | 拿掉硬過濾等於放棄房型／類別／預算／尺寸約束。先查是哪個 clause 造成 0 筆。 |

## 快速對照

| 階段 | 關鍵活動 | 成功標準 |
|-------|---------------|------------------|
| **1. 根因** | 讀錯誤、重現、查改動、蒐集證據 | 弄懂「是什麼」與「為什麼」 |
| **2. 模式** | 找可運作的範例、比對 | 找出差異 |
| **3. 假設** | 形成理論、最小化測試 | 假設被證實或形成新假設 |
| **4. 實作** | 建測試、修、驗證 | 問題解決、驗證通過 |

## 當流程顯示「找不到根因」

若系統化調查顯示問題確實屬於環境性、時序性或外部因素
（本專案常見：HF Hub 限流、Anthropic API 暫時性 5xx、MPS 記憶體不足導致退 CPU）：

1. 你已經完成流程
2. 記錄你調查過什麼
3. 實作適當的處理（重試、逾時、清楚的錯誤訊息；例如金鑰不存在時給出可讀提示而非 traceback）
4. 加上監看／記錄，供日後調查（例如把每次查詢的 `where` 與各階段筆數印出來）

**但是：** 95% 的「找不到根因」其實是調查沒做完。

## 支援技術

以下技術是系統化除錯的一部分，都放在本目錄：

- **`root-cause-tracing.md`** — 沿呼叫堆疊反向追蹤，找到最初的觸發點
- **`defense-in-depth.md`** — 找到根因後，在多層加上驗證
- **`condition-based-waiting.md`** — 用條件輪詢取代隨便設的等待時間

**相關 skills：**
- **sunnydata-testing** — 用來建立會失敗的測試案例（Phase 4 Step 1；本專案 pytest 尚未建置）
- **sunnydata-code-review** — 在宣稱修好之前先驗證修法確實有效

## 真實效益

來自實際除錯經驗：
- 系統化做法：15-30 分鐘修好
- 亂改做法：2-3 小時鬼打牆
- 一次修對率：95% vs 40%
- 新引入的 bug：幾乎為零 vs 家常便飯
