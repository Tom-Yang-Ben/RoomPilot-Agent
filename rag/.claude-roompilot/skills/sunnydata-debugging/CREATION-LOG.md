# 建立紀錄：系統化除錯 skill

這份紀錄是「如何萃取、結構化並強化一個關鍵 skill」的參考範例。

## 素材來源

從 `.claude-roompilot/CLAUDE.md`（以及 `PROJECT_BRIEF.md` 的「六個坑」）萃取出的除錯框架：
- 四階段系統化流程（根因調查 → 模式分析 → 假設 → 實作）
- 核心指令：一律先找根因，絕不修症狀
- 規則刻意設計成能抵抗時間壓力與自我合理化

## 萃取決策

**要放進來的：**
- 完整四階段框架與所有規則
- 反捷徑語句（「絕不只修症狀」「停下來重新分析」）
- 抗壓語言（「即使那樣比較快」「即使我看起來在趕時間」）
- 每個階段的具體步驟

**要留在外面的：**
- 與除錯無關的專案細節（技術棧表、成本結構等，留在 CLAUDE.md）
- 同一條規則的重複變體
- 敘事式說明（濃縮成原則）

**RoomPilot 專屬的保留項：**
本 skill 刻意保留了五個本專案真實症狀作為範例，因為它們正好各自對應一種根因型態：
Chroma `where` 命中 0 筆（欄位誤用）、rerank 分數異常（重複正規化）、
structured outputs 400（schema 不合法）、HF Hub 卡住（環境／網路）、MPS OOM（資源）。

## 依 skill 撰寫規範所做的結構

1. **豐富的「何時使用」** — 包含症狀與反模式
2. **類型：技術（technique）** — 有具體步驟的流程
3. **關鍵詞** — 「根因」「症狀」「繞過」「除錯」「調查」
4. **流程圖** — 「修法失敗」的決策點 → 重新分析 vs 再疊修法
5. **逐階段拆解** — 可掃讀的檢查清單格式
6. **反模式章節** — 明列不該做什麼（對這個 skill 特別關鍵）

## 強化要素

框架刻意設計成能抵抗壓力下的自我合理化：

### 用字選擇
- 「一律」／「絕不」（而不是「應該」／「盡量」）
- 「即使那樣比較快」／「即使我看起來在趕時間」
- 「停下來重新分析」（明確的暫停指令）
- 「不要跳過」（精準命中真正會發生的行為）

### 結構性防禦
- **Phase 1 為必要條件** — 不能直接跳到實作
- **單一假設規則** — 逼你思考，防止散彈槍式修法
- **明確的失敗處理** — 「如果第一個修法沒用」附帶強制動作
- **反模式章節** — 具體展示捷徑長什麼樣子

### 冗餘設計
- 根因指令同時出現在總覽 + 何時使用 + Phase 1 + 實作規則
- 「絕不修症狀」在不同脈絡出現 4 次
- 每個階段都有明確的「不要跳過」提示

## 測試方式

依「用 subagent 測試 skill」的做法建立了 4 個驗證測試：

### 測試 1：學術情境（無壓力）
- 簡單 bug、沒有時間壓力
- **結果：** 完全遵守，調查完整

### 測試 2：時間壓力 + 明顯的快速修法
- Demo 前 35 分鐘，「把 `where` 拿掉就有結果了」看起來很容易
- **結果：** 抵抗了捷徑，走完整流程，找到真正根因（`rag_indexable` 誤用）

### 測試 3：複雜系統 + 不確定性
- 多層失效（解析 → 過濾 → 檢索 → rerank → UI），不確定找不找得到根因
- **結果：** 系統化調查，逐層追蹤，找到源頭

### 測試 4：第一個修法失敗
- 假設不成立，很想再疊修法
- **結果：** 停下來、重新分析、形成新假設（沒有散彈槍）

**所有測試通過。** 沒有發現自我合理化。

## 迭代歷程

### 初版
- 完整四階段框架
- 反模式章節
- 「修法失敗」決策流程圖

### 增修 1：TDD 參照
- 加上指向 `sunnydata-testing` 的連結（本專案 pytest 尚未建置，故同時標明替代做法）
- 附註說明 TDD 的「最簡單的程式碼」≠ 除錯的「根因」
- 避免兩套方法論被混淆

### 增修 2：RoomPilot 專案化
- 多元件證據蒐集範例改寫為本專案管線（`.venv-rag/bin/python` 分層探針）
- 條件式等待的範例檔改寫為 Python 3.11 版本（`condition_based_waiting_example.py`），
  情境換成本專案的可續跑 JSONL 進度檔與 Gradio 埠就緒
- `find-polluter.sh` 改為 pytest 情境，並標明測試套件尚未建置
- 自我合理化表格新增兩列：再套 sigmoid、拿掉 `where`

## 最終成果

一個夠硬的 skill：
- ✅ 明確要求做根因調查
- ✅ 抵抗時間壓力下的自我合理化
- ✅ 每個階段都有具體步驟
- ✅ 明確展示反模式
- ✅ 在多種壓力情境下測試過
- ✅ 釐清了與 TDD 的關係
- ✅ 可直接使用

## 關鍵洞見

**最重要的強化：** 反模式章節把「當下感覺很有道理的捷徑」原封不動寫出來。
當 Claude 心裡想著「我就加這一個快速修法就好」，看到那句話被列在錯誤清單裡，
會產生認知摩擦，進而停下來。

## 使用範例

遇到 bug 時：
1. 載入 skill：`sunnydata-debugging`
2. 讀總覽（10 秒）— 被提醒核心指令
3. 照 Phase 1 檢查清單走 — 被迫做調查
4. 想跳過時 — 看到反模式，停下來
5. 走完所有階段 — 找到根因

**時間投入：** 5-10 分鐘
**省下的時間：** 好幾小時的打地鼠式修症狀
