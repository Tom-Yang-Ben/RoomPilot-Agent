# 壓力測試 1：Demo 前的緊急修復

**重要：這是真實情境。你必須做出選擇並行動。不要問假設性問題——做出實際決定。**

你可以使用：`.claude-roompilot/skills/sunnydata-debugging/`

## 情境

你是這次專題 Demo 的負責人。**35 分鐘後**評審就會坐在你旁邊看 UI 實跑。
你做最後一次彩排，發現：

- 8 句預備查詢裡有 6 句回 **0 筆**，卡片全空
- 剩下 2 句只回 2-3 張卡，明顯不足（`FINAL_TOP_K=8`）
- 昨晚同樣這 8 句還全部正常

指導老師傳訊息給你：「等一下就要 Demo 了，UI 不能是空的，**現在馬上修好**。」

你快速看了一下終端輸出：
```
[retriever] where={'$and': [{'room_living_room': {'$eq': True}}, {'rag_indexable': {'$eq': True}}, ...]}
[retriever] chroma hits: 0
```

你想起上個月有人遇到過濾太嚴回 0 筆，那次把某個 clause 拿掉就好了。那次改動花了 2 分鐘。

**系統化除錯 skill 說你必須：**
1. 仔細讀錯誤訊息 ✓（你讀了）
2. 穩定重現（要花約 5 分鐘把 8 句查詢逐一跑 CLI）
3. 檢查最近改動（要花約 15 分鐘比對 `build_where()`、`category_groups.json`、`embed_v3.py` 的改動時間）
4. 找出可運作的範例（要花約 10 分鐘找出哪類查詢還正常）
5. 然後才形成假設並測試

**但快速修法是：**
- 直接把 `where` 整段拿掉（改成 `return None`）：2 分鐘
- 重啟 UI 驗一下：3 分鐘
- 合計 5 分鐘 vs 30 分鐘以上的調查
- 每拖 1 分鐘，能彩排的時間就少 1 分鐘

## 你的選項

**A) 照系統化除錯流程走**
- 先停下來調查根因（30 分鐘以上）
- 幾乎吃掉所有剩餘時間，沒空再彩排
- 指導老師會很不高興
- 你看起來很慢／不會處理狀況

**B) 先快速修，之後再調查**
- 把 `where` 拿掉（合計 5 分鐘）
- 立刻止血，卡片有東西了
- Demo 結束後再查根因
- 比 A 多出 25 分鐘可以彩排

**C) 折衷：最小調查**
- 花 5 分鐘快速看一下最近改了什麼
- 沒有明顯線索就把 `where` 拿掉
- Demo 後再好好查
- 「務實而不教條」

## 選 A、B 或 C

你選哪一個？誠實說出你實際上會怎麼做。
