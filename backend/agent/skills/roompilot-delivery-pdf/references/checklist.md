# 交付前檢查清單

`preflight_check.py` 會自動跑掉大部分機械性的檢查。這份清單是**腳本抓不到、必須自己看過一遍**的項目。

出檔前實際打開 PDF 逐頁看過。屋主會看到的東西你自己沒看過，是最容易出事的情況。

## 資料正確性

每個尺寸都能在 `configuration_snapshot` 或 `layout_json` 裡找到出處。`preflight_check.py` 的數字溯源會標出可疑的，被標到的要真的回去查，不要因為「看起來合理」就放行。

家具名稱與實際選用的型號一致，沒有把「三人沙發」寫成「L 型沙發」這種圖文不符。對照圖片再看一次規格表。

生圖失敗的房間，`appendix.limits` 有寫。看 `manifest.json` 的任務狀態，不要只看資料夾裡有沒有圖。

沒有把「建議」寫成「已完成」。這份文件描述的是既有方案，任何新想法都應該在 `next_steps.notes` 裡，措辭是「建議討論」而非「已規劃」。

## 圖文對應

每張主視覺圖確實是那個房間的。房名資料夾對錯是很常見的失誤，而屋主一眼就會看出來。

圖說（`hero_caption`）描述的方向與圖片一致。寫「自玄關方向望向南面」就真的要是那個角度。

同一個空間的多張圖沒有重複放同一張。

## 文案品質

`preflight_check.py` 會抓廣告腔、AI 高頻詞、句尾空修飾語與句長單調，但它是關鍵字比對，抓得到的只是一部分。完整規範見 `writing-rules.md`，以下是必須人工判斷的：

大聲讀一次。讀起來卡住、或自己都覺得有點油的句子，就是要改的地方。這一步比任何清單都有效。

通篇看有沒有八個房間都用同一個句型開頭。有的話至少改掉一半。

把八頁空間篇章並排看，有沒有一整句在每一頁重複出現（配色原則、地板牆面材質這種全案共用的事實）。腳本只抓得到一字不差的重複，換個說法再講一次它抓不到，但屋主感覺得出來。

設計總論的每一條真的對得上後面某一章，而且講的是那一章的**內容**，不是「該章包含樣貌、選件依據與規格表」這種每章都成立的話。

`look` 讀起來是「走進去會看到什麼、待著是什麼感覺」，不是家具清單分行寫。屋主看圖就知道有沙發，你要寫的是圖上看不出來的東西。

句子長度有沒有變化。連續三句長度接近就刻意插一個短句進去。

至少有一到兩處誠實的取捨說明（「本來可以…但那樣會…所以我們選擇…」）。整份都在誇自己會讀起來像廣告。

`rationale` 裡引用屋主需求的地方，屋主真的說過。編造需求比不寫需求更糟。

有沒有「不只是……更是……」這類否定式排比，或硬湊成三項的列舉。兩項或四項通常更誠實。

結尾寫的是接下來會發生什麼事，不是祝福。

## 版面

翻一次 PDF，看有沒有孤行——一個章節只剩一兩行掉到下一頁。有的話把該空間的 `look` 或 `rationale` 精簡一兩句通常就解決了。

規格表沒有被切在跨頁中間。

封面主視覺是全案最好看的一張圖。這張圖決定屋主打開檔案前三秒的印象，值得挑。

## 檔案

檔名格式：`<案名>_室內設計提案_<版本>.pdf`。不要用 `output.pdf`、`final_v2_真正最終.pdf`。

檔案大小。渲染圖多的案子容易超過 20 MB，寄信會被擋。太大的話先把 PNG 轉成品質 85 的 JPG 再重跑 `build_pdf.py`。

PDF 能在別的裝置打開、中文沒有變成方框。`preflight_check.py` 會抓豆腐字，但實際開一次最保險。
