# RoomPilot 交付提案 PDF

## 這份文件在做什麼

RoomPilot 跑完八步，屋主手上會有一堆渲染圖和一包 JSON。圖很漂亮，但圖不會替自己說話——屋主看到客廳照片，不會知道沙發為什麼擺在那個位置、為什麼走道留 90 公分、為什麼選了那個色卡。**這份 PDF 的工作就是把「設計判斷」翻譯成屋主聽得懂、而且會點頭的話。**

所以這不是一份規格書。判斷標準是：屋主看完會不會覺得「這個設計是為我做的」，而不是「這是電腦生的」。

## 流程

分三段走，中間不要跳步。文案是慢工，排版和檢查交給腳本。

### 一、蒐集素材

```bash
python3 <skill>/scripts/collect_context.py <成果包或專案資料夾> -o report_data.json
```

會產出 `report_data.json`：來源檔（`configuration_snapshot` / `render_brief` / `manifest` / `scene_json`）、逐房圖檔清單、常用欄位的模糊索引，以及一份 `gaps`（找不到什麼）。

腳本只負責找和對，不做詮釋。**接著一定要親自讀 `report_data.json` 的 `sources[*].raw`**，特別是家具清單、尺寸、材質、色卡與視角——文案裡的每個數字都要來自這裡。`gaps` 裡列出的東西如果影響到你要寫的內容，去問使用者，不要自己補一個聽起來合理的數字。欄位對應細節見 `references/data-contract.md`。

### 二、寫 content.json

這是唯一需要動腦的部分。欄位見 `references/content-schema.md`，文案規範見 `references/writing-rules.md`，好壞對照見 `references/room-copy-examples.md`——**第一次寫之前先讀後兩份**，那裡的對照組比任何抽象規則都有用。

順序建議：先把每個空間的 `look`（長什麼樣）和 `rationale`（為什麼）寫完，再回頭寫 `statement`（設計總論）。總論是從各空間的共同判斷歸納出來的，先寫總論容易寫成空話。

**篇幅有上限。** 一個空間一頁是這份文件的節奏，超過就會出現整頁只有一張表格的殘頁。抓這個量：`look` 約 100–140 字、`rationale` 兩條（每條 `body` 60–90 字）、`specs` 三到五列、`extra_images` 只給客廳與主臥這種重點空間。寫超過不會被擋，但排版會醜。

**出第二版時加 `whats_new` 區塊。** 它會排在封面後的第一頁，逐條回應屋主的回饋。屋主打開 v2 最想知道的就是「我上次說的那件事你改了沒」，那不能放在第 17 頁。

### 三、排版與檢查

```bash
python3 <skill>/scripts/build_pdf.py content.json -o "<案名>_室內設計提案_v1.pdf" --base-dir <成果包資料夾>
python3 <skill>/scripts/preflight_check.py content.json --pdf "<案名>_室內設計提案_v1.pdf" --data report_data.json --base-dir <成果包資料夾>
```

`build_pdf.py` 擁有版面與品牌樣式，你只負責文字——**不要自己另外寫 HTML 或改 CSS 產 PDF**。每份交付文件的視覺要一模一樣，屋主才會覺得這家公司有在做事；每次重排也是純粹浪費時間。要調品牌樣式改 `assets/tokens.css`，理由見 `references/design-tokens.md`。

`build_pdf.py` 跑完會自己回報三件事：**孤行殘頁**（哪一頁內容太早結束、該怎麼精簡）、**幾乎純色的圖**（多半是還沒產生的圖面，不要當成有效圖排進去）、以及文字層碼位的修正。有殘頁就照它的建議精簡文案重跑，不要靠加字填滿。

`preflight_check.py` 是交付前的自我檢查：圖檔存不存在、有沒有佔位字、數字能不能溯源、有沒有建案廣告腔與 AI 味、中文有沒有變豆腐字。**有 FAIL 就修到過為止再交出去**，腳本抓不到的人工項目見 `references/checklist.md`。

## 寫文案的原則

完整的規範在 `references/writing-rules.md`（說服力原則 + AI 痕跡清除清單），好壞對照在 `references/room-copy-examples.md`。**動筆前兩份都要讀。** 這裡只放最核心的四條：

**寫屋主的生活，不要寫家具的位置。** 「沙發置於南側牆面，前方留設 900mm 通道」是給施工看的；「你從玄關進門會先看到整面南向的光，沙發背對走道，回家坐下時不會有人從背後經過」才是給屋主看的。同一件事，後者讓人想住進去。技術規格不是不能寫，是放到 `specs` 表格裡去，別跟敘述混在一起。

**每個「為什麼」都要接回屋主自己說過的話。** 屋主在第 5 步問卷填了「有兩個小孩」「常在家工作」「討厭收納外露」，這些就是 `rationale` 的彈藥。「因為你提到常在家開會，書房的桌子背後刻意留白，視訊時鏡頭裡不會出現雜物」——這種句子屋主無法反駁，因為那是他自己講的。找不到問卷依據時，退回到空間本身的客觀條件（採光方位、開間深度、動線長度），也不要編一個需求出來。

**寫出取捨，不要只寫優點。** 「這裡本來可以再塞一個櫃子，但那樣走道會縮到 70 公分，兩個人錯身會卡住，所以我們選擇留白」——承認取捨反而讓人相信你真的算過。整份文件都在誇自己，讀起來像廣告；有一兩處誠實的取捨，其他的誇獎才有重量。

**不要有 AI 味，也不要有建案廣告味。** 這兩件事在室內設計文案裡幾乎是同一件事，因為訓練資料裡塞滿了建案文宣。句尾不要掛「，營造出……」「，展現了……」；不要用「打造」「坐落於」「匠心」「極致」「療癒」；不要寫「這不只是一張沙發，更是……」；不要把東西硬湊成三項。判準很簡單：把那串修飾刪掉，句子的資訊量有沒有變少？沒有就是贅字。`preflight_check.py` 會自動抓一部分，但抓不完，還是要自己讀一次。

**數字要精確，形容詞要克制。** 「3.6 米開間」「淨高 2.7 米」「離牆 45 公分」比「寬敞舒適」有力十倍。但**每個規格都要有出處，而規格不只是尺寸**——色溫、照度、演色性、百分比、以及「可拆洗」「防滑」這類材質性能宣稱都算。這類句子最容易不小心寫出來，因為它們聽起來像常識；資料裡沒有就寫「待選樣確認」。

**中文為主，專有名詞中英並陳。** 材質、工法、家具型號保留英文方便發包：`橡木海島型地板 (oak engineered flooring)`、`亞麻布沙發 (linen upholstery)`。中文內文不要夾雜半吊子的英文形容詞。

**不確定就標明，不要圓場。** 資料裡沒有的東西——沒選定的燈具、還沒確認的材質——寫進 `next_steps.notes` 或 `appendix.limits`，用「待現場確認」講清楚。屋主發現一個編造的細節，整份文件的可信度就沒了。

**屋主問了資料回答不了的問題**（最常見的是預算），不要用一句話打發。給它應有的篇幅：說明為什麼現在給不出數字、需要先確認哪些事、什麼時候可以給。誠實地把問題攤開，比含糊帶過更能建立信任。

## 文件結構

`build_pdf.py` 依 `content.json` 有哪些區塊自動排；缺的區塊會跳過，不會留空白頁。標準順序：

封面 → 設計總論（一段 hook + 三個設計主張）→ 全案速覽（坪數格局風格 + 平面圖）→ 逐空間篇章（每空間一頁：主視覺、生活場景句、長什麼樣、為什麼這樣設計、關鍵配置表）→ 色彩與材質 → 燈光與氛圍 → 接下來（下一步、檔案清單、已知限制、版本）。

空間順序照屋主的動線走：玄關 → 客廳 → 餐廳 → 廚房 → 主臥 → 次臥 → 衛浴 → 陽台。公共空間放前面，因為那是屋主最在意也最會拿給別人看的部分。

## 常見狀況

**某些房間生圖失敗、沒有圖。** 照樣寫那個空間的篇章，`hero_image` 留空會自動變成佔位框，並在 `appendix.limits` 說明「此空間渲染任務失敗，圖面待補」。刪掉整個房間會讓屋主以為你漏了。

**使用者只丟了幾張圖，沒有完整成果包。** `collect_context.py` 會退回掃描模式把圖列出來。這時規格與尺寸多半缺，就把 `specs` 留空、專心寫 `look` 與 `rationale`，並在限制裡註明「本版未含尺寸規格」。

**平面圖或某張圖是空白的。** `build_pdf.py` 會警告「幾乎是純色」。不要把它當成有效圖面排進去——屋主會看到一塊空白然後開始懷疑其他頁。改用面積表或文字說明代替，並在 `appendix.limits` 寫明那張圖還沒產生。

**要出第二版。** 用 `whats_new` 區塊逐條回應屋主回饋，它會排在封面之後。回饋裡如果有資料回答不了的（預算、還沒決定的做法），照樣列出來，說明現在給不出答案的原因與需要先確認什麼，不要跳過那一條——屋主會發現。版本號同時寫進 `meta.cover_meta` 與檔名。
