## §2 修好 503：換環境必看

### 症狀

合併後第 6 步進不去。`POST /api/scene/generate` 一直回 **503**：

```
code:   runtime_catalog_unavailable
reason: relation "roompilot.runtime_catalog_imports" does not exist
```

### 原因

ben 帶進來一個「嚴格模式」。`backend/catalog/runtime_catalog_repository.py:49` 的註解直接寫著 *"Return strict postgres by default"*——

`ROOMPILOT_RUNTIME_CATALOG_PROVIDER` **沒設定時預設 `postgres`**，而 postgres 是嚴格模式：**讀不到資料表就回 503，不會靜默退回 JSON**。

本機 PostgreSQL 只有家具相關的 11 張表，**沒有 Kai 的 Phase 4 runtime catalog，也沒有 `roompilot.projects`**。

ben 自己的 `.env.example` 就標註了「本機尚未匯入時請改成 json」，只是舊 `.env` 從來沒有這兩個欄位。

### 解法（已套用，備份 `.env.bak-premerge-20260731`）

```bash
ROOMPILOT_RUNTIME_CATALOG_PROVIDER=json
ROOMPILOT_PROJECT_STORE_PROVIDER=sqlite
```

⚠️ **換到公司電腦合併後會再撞一次同樣的問題**，直接照抄這兩行。

### 驗證

```
POST /api/scene/generate    503 → 200，耗時 3.97 秒
五支端點 smoke              全部 200
POST /api/projects          201
```

## §4 家具擺出來了，但擺不對（本檔重點）

### 實測資料

房間 420×360 cm（座標以房間中心為原點，x 範圍 −210~210，z 範圍 −180~180）：

| 家具 | 佔用範圍 | 判定 |
|---|---|---|
| 床 | x[−46~46] z[−30~**172**] | ✅ 床頭貼後牆（牆在 180） |
| **床頭櫃** | x[**100**~180] z[91~138] | ❌ 床邊緣在 x=46，床頭櫃從 x=100 才開始——**中間空 54 公分** |
| **床頭櫃** | z 中心 114.5 | ❌ 床頭在 z=172，床頭櫃卻在床的**腰部**旁邊 |
| **地毯** | x[−125~125] z[31~111] | ❌ **整片壓在床底下** |
| 書桌 | z[−172~−62] | ✅ 貼前牆 |
| 書櫃 | x[−202~−170] 轉 90° | ✅ 貼左牆 |

`placement.failed = []`、`unavailable_types = []`——**引擎認為五件全部擺放成功**。位置合法，但不合理。

### 根因一：沒有人告訴引擎「誰要貼著誰」

引擎**有**成組擺放的能力：`placement.py:162` 的 `place_adjacent_to_furniture()`。

但要用它，家具身上必須帶一張標籤：

```python
placement_relation = { "kind": "adjacent", "target_types": ["bed", ...] }
```

觸發條件在 `scene_service.py:1550`：

```python
elif (item.get("placement_relation") or {}).get("kind") == "adjacent":
```

**實測那五件家具的 `placement_relation` 全部是 `None`。**

唯一會貼標籤的地方是 `main.py:3072`，而且只貼給三種東西：

| 誰有標籤 | 標籤內容 |
|---|---|
| 地毯 | `kind: "under"`（壓在沙發／床下面） |
| 植栽 | `kind: "adjacent"` |
| 燈 | `kind: "adjacent"` |

**床頭櫃、餐椅、茶几、電視櫃——一個都沒有。**

所以床頭櫃走的是「找個空位塞進去」的通用路徑：它只知道「不能撞到別人」，不知道「我應該貼在床頭旁邊」。

### 根因二：引擎沒有「貼哪一端」的概念

就算標籤補上了，`place_adjacent_to_furniture()` 目前只會「放在主家具四周」（原始碼註解就是這樣寫的），**沒有「床頭 vs 床尾」的分辨能力**。

床頭櫃必須貼**床頭**那一端，貼床尾是錯的。這是引擎本身要補的能力。

### 根因三：地毯壓床下＋跳過碰撞檢查

地毯的標籤是 `kind: "under"`，所以整片蓋在床下是照規則跑的。但：

1. 這片是**走道地毯**（runner，249×80 長條形），照理該擺在床的側邊走道，不是壓在床下
2. 地毯目前靠 `_IGNORE_COLLISION_TYPES` **完全跳過碰撞檢查**——這是 2026-07-23 總帳裡自己記的「偷吃步」

**這一項正好對應四大設計裡的「堆疊層」。**

### 小結

| # | 問題 | 在誰的地盤 |
|---|---|---|
| 1 | 沒有人給床頭櫃等家具貼「要貼著誰」的標籤 | `main.py`（Bella） |
| 2 | 引擎不會分辨「貼床頭還是床尾」 | **引擎（自己）** |
| 3 | 地毯壓床下＋跳過碰撞 | **引擎（自己）**＝堆疊層 |

⚠️ **「成組擺放」不在 2026-07-23 的四大設計清單裡**，但它對「擺得對」的影響最大。建議升級為第五項。

### 狀態全綠

```
enabled/ready: true    blockers: []
parser:    openrouter / openai/gpt-4o-mini
models:    BAAI/bge-m3 (1024 維) + bge-reranker-v2-m3，兩者已快取，device=cpu
database:  postgresql_pgvector，7,958 筆 embeddings
```

### 測試一：單品查詢 ✅ 完全正確

查「北歐風淺色木紋雙人床，房間約 4 米寬」→ 8 筆命中，全是床、全是北歐風。

LLM 解析精準：`room_type: bedroom`、`styles: [scandinavian]`、`pattern: 木紋`、`max_width_cm: 400`。

### 測試二：多品項查詢 ❌ 抓到 bug

查「客廳想要現代簡約風的沙發加茶几和電視櫃」：

| 品項 | 命中 |
|---|---|
| 沙發 | ✅ 4 |
| 茶几 | ✅ 4 |
| **電視櫃** | **❌ 0** |

### 根因：AI 猜的「主角／配角」標籤被當成硬過濾

家具在資料庫裡有一個 `role` 標籤，只有兩種：`anchor`（主角）／`accent`（配角）。

| 分類 | 資料庫實際 | LLM 給的 filter |
|---|---|---|
| 茶几 | `accent` 203 件 | `accent` → ✅ |
| **電視櫃** | **`anchor` 52 件** / accent 4 | `accent` → ❌ |
| 電視與影音家具 | **`anchor` 10 件** | `accent` → ❌ |

SQL 驗證：

```
全部電視櫃類            66 件
role='accent'            4 件
accent 且在價格帶內       0 件   ← 回 0 的直接原因
anchor 且在價格帶內      38 件   ← 全被 role 過濾丟掉
```

**38 件完全合格的電視櫃被丟掉，而且不報錯。**

`role` 在 `models.py:50` 定義為 `Literal["anchor","accent"]`，但 `category_groups.json` 的 group 定義**沒有指定 role**——所以它是 **LLM 每次自己猜的**。猜錯的值被當成 SQL 硬過濾，且歸零時沒有退場機制。

分類名稱、房型對照、embedding 覆蓋、價格帶都逐項驗過正常，只有 role 這關卡死。

### 這同時是契約問題

`backend/spatial_data/AGENTS.md` 明寫：

> 家具 RAG 可解析需求、檢索並排序 Kai catalog 家具，但**不得決定選件政策**、擺位、碰撞、淨空或合法性。

`role` 正在實質決定「哪些家具進得了候選清單」——這已經是選件政策，超出 RAG 該做的事。**可以拿這條去跟 Django 談。**

### 三種修法（都在 Django 地盤，不可自行改）

1. `role` 改成**只用來排順序**，不用來擋人（猜錯頂多順序差，不會整個消失）
2. 過濾後為空時**自動放寬再查一次**，回應標記 `relaxed_filters`
3. 在 `category_groups.json` **為每個 group 寫死 role**，不讓 LLM 猜 ← **最符合「LLM 不做決定性判斷」的紅線**

### 效能：慢，但不是冷啟動

```
第一次  parse 5.6s + retrieve_and_rerank 33.8s = 39.9s
第二次  parse 7.4s + retrieve_and_rerank 35.8s = 43.8s
```

第二次沒變快 → **不是模型載入慢，是 CPU 跑 reranker 本身慢**。
`.env` 仍是 `ROOMPILOT_RAG_DEVICE=cpu`，**GPU（RTX 2060）還是沒開**，舊筆記的 P0 仍未做。
