## §0 三分鐘上手

**現在的位置**：家具**擺得出來**了，但**擺得不對**。引擎只會回答「這裡合不合法」，不會回答「這裡好不好」。

**最重要的一句話**（2026-08-01 下午查出，推翻先前認知）：

> **擺放策略不在 `backend/engine/`，在 `backend/server/scene_service.py`。**
> 引擎的 `place_furniture()` 只是**備援**——scene_service 自己那張候選表全部失敗才輪得到它。

這代表：**只改引擎，第 6 步幾乎不會變**。不是因為「要等前端」，是因為策略住在錯的檔案裡。

**三方分工**（Ancai 親口定義，不要用別的說法覆蓋）：

| 角色 | 職責 |

| **引擎**（Ancai） | 家具規則：淨空、碰撞、合法性、座標 |

## §3 為什麼「擺不對」——完整因果鏈（08-01 實測）

### 3.1 根因零：擺放策略住在 `scene_service.py`，不在引擎

第 6 步的真實呼叫路徑：

```
POST /api/scene/generate
  → scene_service.generate_layout()            :1396
      → scene_service._placement_candidates()  :717  ← 80 行寫死的候選位置＋角度表，涵蓋 17 種家具
      → 逐個候選丟 engine.check_placement_with_clearance() 驗證
      → 全部失敗才 → engine.place_furniture()  :1654  ← 引擎只是備援
```

`scene_service` 自己還擁有：

- `_WALL_ANCHORED_TYPES`（:697）— **貼牆清單也在這裡**
- `_WINDOW_CLEARANCE_EXEMPT_TYPES`、`forbidden_zones` — 窗前禁放帶也在這裡
- `_hinted_wall_candidate` — 牆面提示

👉 **07-29 就寫過這件事**：「沿牆／網格找可放位置——大半 `scene_service`——『能不能放』的搜尋屬幾何」，並列為「適合收回 engine」。擱置至今。

👉 **對應的後果**：改 `backend/engine/placement.py` 不會讓第 6 步變好，因為輪不到它執行。

### 3.2 方向其實已經對了一半（好消息）

實測（房間 400×300，衣櫃 100×60，前方淨空 90，貼下牆）：

```
rotation=0   （正面朝房間內）→ legal = True
rotation=180 （正面朝牆）    → legal = False
```

正面朝牆時，90 公分的開門淨空會跑到牆外，引擎自己就擋掉了。

👉 **有前方淨空的 16 個類型只要貼牆，方向自動正確**：衣櫃、PAX 衣櫃、櫃體、收納系統、抽屜櫃、餐邊櫃、電視櫃、電視影音、展示櫃、鞋櫃、鏡櫃、泛用收納、書櫃、層架、書桌、衣帽架。

👉 **方向會亂轉的只有沒設前方淨空的**：沙發、床、床頭櫃、茶几、單椅、餐椅。

👉 這同時解掉 07-29 待驗證點 #2「靠牆衣櫃 front 是否朝室內？寫測試證明」——**答案是會，且已由引擎自動保證**。

### 3.3 真正的洞：貼牆完全沒強制

```
衣櫃放在 400×300 房間正中央 → legal = True
引擎自己找位置             → 就放在正中央 (200,150)
```

`placement.py:_candidate_placements()` 的搜尋順序是 **先試房間正中央**，再掃四面牆，**第一個合法的就採用**。

### 3.4 沒有人告訴引擎「誰要貼著誰」

引擎**有**成組擺放能力（`placement.py:162` `place_adjacent_to_furniture()`），但要家具帶標籤：

```python
placement_relation = { "kind": "adjacent", "target_types": ["bed", ...] }
```

唯一會貼標籤的地方是 `main.py:3072`，而且只貼給**地毯（under）／植栽（adjacent）／燈（adjacent）**。
床頭櫃、餐椅、茶几、電視櫃——**一個都沒有**。

而且就算標籤補上，`place_adjacent_to_furniture()` 只會「放在主家具四周」，**沒有床頭 vs 床尾的概念**。

### 3.5 沙發前方無約束（07-29 的設計債）

07-29 拍板「沙發不設前方淨空，前方是茶几關係（E11），不是淨空」。
但**關係約束從來沒做**，所以沙發前方現在是**完全無約束**——這就是沙發亂擺、茶几跑到最遠那面牆的原因。

## §7 資料事實（查證過，直接引用）

### 7.1 引擎規則 × 資料庫對帳（08-01 實跑）

引擎 23 個類型有淨空規則，資料庫 55 個分類。

**A. 死鍵（引擎有規則，資料庫沒這分類）**

```
❌ bed-frame          資料庫裡床只叫 bed（110 件）
❌ cabinets-cupboard  資料庫裡叫 cabinet-cupboard（少一個 s，146 件）
```

更麻煩的是 `scene_service.py` 的別名表**正在使用這兩個死名字**：

```
:124  "床架"   → "bed-frame"          → 撈到 0 件
:132  "收納櫃" → "cabinets-cupboard"  → 撈到 0 件
```

使用者在問卷打「床架」或「收納櫃」，系統**安靜回 0 件不報錯**。清死鍵**不能只動 engine**。

**B. 對得上：21 個分類，1,820 件** ✅

**C. 沒規則：34 個分類，6,138 件——大部分刻意**

| 分堆 | 件數 | 說明 |
|---|---|---|
| 故意不設 | ~5,100 | 凳子長凳 1365（桌子配套）、沙發 1828（用關係不用淨空）、地毯 993（地面層允許被壓）、茶几 196、軟裝 642、壁架 55、椅子 683 |
| **真的漏掉** | ~300 | ⚠️ **`bedside-table` 54**、`room-divider` 17、`mirror`+`large-mirror` 92、兒童家具四類 87 |

👉 **不要因為件數多就去補沙發／椅凳／地毯**，那會推翻 07-29 的設計決定。

### 7.4 RAG 已知 bug（Django 地盤，只追蹤）

查「客廳想要現代簡約風的沙發加茶几和電視櫃」→ 沙發 ✅4、茶几 ✅4、**電視櫃 ❌0**。

根因：LLM 每次自己猜的 `role`（`anchor`／`accent`）被當成 SQL 硬過濾。

```
全部電視櫃類        66 件
role='accent'        4 件
accent 且在價格帶內   0 件   ← 回 0 的直接原因
anchor 且在價格帶內  38 件   ← 全被丟掉，且不報錯
```

`backend/spatial_data/AGENTS.md` 明寫 RAG「**不得決定選件政策**」，`role` 正在實質決定候選——已超界，可拿這條去談。

**效能**：parse 5.6~7.4s + rerank 33.8~35.8s ≈ **40 秒**。第二次沒變快 → 不是冷啟動，是 CPU 跑 reranker 慢。`.env` 仍 `ROOMPILOT_RAG_DEVICE=cpu`，**RTX 2060 沒開**。
