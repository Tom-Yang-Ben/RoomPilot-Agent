## §2 實測一：Agent LLM 選件「結構上不可能執行」

### 實測方式

照前端 `scene_v2.js:6563` 的 payload 格式實際 POST：

```bash
curl -X POST http://127.0.0.1:8002/api/agent/furniture/select \
  -H 'Content-Type: application/json' \
  -d '{"rooms":[{"room_id":"r1","room_type":"bedroom","label":"主臥"}],
       "offers":{"r1":[{"furniture_id":"f1","normalized_type":"bed"}, ...]},
       "style_id":"scandinavian","context":{}}'
```

### 結果

```json
{"source": "local_rules", "model": null, "warnings": []}
```

### 根因（兩層）

`backend/server/main.py:2373`：

```python
if isinstance(llm_selection, dict):          # ← 前端從不送這個欄位
    request_selections(..., complete=lambda _msgs: (..., llm_selection))
```

1. 前端 POST body 只有 `rooms` / `offers` / `style_id` / `context`，**沒有 `llm_selection`** → 這個 `if` 永遠不成立。
2. 就算成立，注入的 `complete` 只是把呼叫端自己傳進來的答案原封不動回傳——**它不打 OpenRouter**。

再確認 `backend/agent/select.py`：**整個檔案沒有任何 HTTP / OpenRouter 呼叫**，`complete=None` 直接 `raise SelectionUnavailableError`。

> **結論**：這是一條「插座裝好、沒接線、電線也還沒買」的電路。OpenRouter key 有效且 `enabled: True`，但選件這條路上沒有東西會去用它。

### 三段電路狀態

| 段 | 狀態 | 證據 |
|---|---|---|
| 選件（放哪些家具） | 🔴 斷 | 端點永遠 `source: local_rules` |
| 擺位（座標） | ✅ 通 | `resolve_placements` 實際執行，4 件全部 `placement_failed: false` |
| 場景規劃 LLM（風格） | ⚠️ 通但極慢 | 見 §4 |

## §4 實測三：「卡」的真凶是 LLM，不是資料量

| 測項 | 耗時 |
|---|---|
| `POST /api/scene/generate` 第 1 次 | **25.6 秒** |
| 同一支第 2 次 | **77.9 秒**（更慢，排除快取／冷啟動） |
| `build_scene_plan()`（含 LLM）單獨計時 | **23.75 秒** |
| `fallback_plan()`（純本地規則） | **0.0000 秒** |

`.env` 的 `OPENROUTER_MODELS` 六個模型**全是 `:free`**，免費層需排隊，故第二次反而更久。

### 第二層卡點：前端 N+1 查詢

`scene_v2.js:7925`：

```js
const selectedFurniture = await Promise.all(placeableFurniture.map(resolveCatalogFurniture));
```

`resolveCatalogFurniture`（:7866、:7869）每件家具打 **1～2 次** `/api/furniture?page_size=80&detail=scene`，每次約 90 KB。

- 30 件家具 → 30～60 次 HTTP 請求、2.7～5.4 MB
- 瀏覽器同網域併發上限 6 條 → 排隊
- 回來後還要在瀏覽器跑 `rankCatalogFurniture()` 逐件打分

此即上午紀錄所稱「第 6 步叫『RAG』的其實是瀏覽器裡的 JS 打分」——它不只不準，也是卡頓來源之一。

### 無逾時保護

`scene_v2.js:445` 的 `api()` 是裸 `fetch()`，**沒有 timeout、沒有進度提示**。使用者只會看到畫面卡住 24～78 秒，不知發生什麼事。

## §5 實測四：2D/3D 空白的完整因果鏈（本次最重要）

### 證據來源

`.runtime/projects.sqlite3` 中使用者實際存檔的專案（name=`123`，`1c2862a8…`，更新於 2026-07-31T07:47Z）。

### 存檔實況

```json
"roomId": "room-1",
"roomType": "default",       ← 沒有房型
"roomLabel": "空間 1",        ← 名稱也無關鍵字

```

```json
"layout_2d": { "furniture": [] }                    ← 0 件
"white_model_3d": { "diagnostics": {
    "requestedFurnitureCount": 0,                   ← 從未要求過家具
    "visibleFurnitureCount": 0,
    "fallbackFurnitureCount": 0,
    "failedFurniture": []                           ← 不是放失敗

```

**關鍵**：`failedFurniture` 為空、`fallbackFurnitureCount` 為 0——**不是擺放失敗，是根本沒產生過家具**。

### 因果鏈（`scene_layout2d.js:214-246`）

```js
function roomTypeFromName(room) {
  const explicitType = room.type || "default";
  if (!["default","unknown","other"].includes(explicitType)) return explicitType;
  //  ↑ "default" 被排除，改用名稱關鍵字比對
  const label = room.label;                    // "空間 1"
  const rules = [["bedroom", /臥室|主臥|次臥|bedroom/], ["living_room", /客廳/], ...];
  return rules.find(...)?.[0] || "default";    // 「空間 1」不符任何一條 → "default"
}

export function recommendedFurnitureForRoom(room) {
  const roomType = roomTypeFromName(room);     // "default"
  const recommendations = { living_room:[...], bedroom:[...], ... };
  return recommendations[roomType] || [];      // "default" 不在表內 → []
}
```

```
房間 roomType="default"、label="空間 1"
   ↓ recommendedFurnitureForRoom() 回 []
specs = [] → 一件家具都沒建立
   ↓
layout_2d.furniture = 0 件
   ↓
diagnostics.requestedFurnitureCount = 0
   ↓
第 6／7 步畫面空白（且無任何錯誤訊息）
```

### 立即可用的臨時解法

第 4 步將房間名稱改為含關鍵字的中文，regex 認得：

| 名稱含 | 對應房型 | 自動放 |
|---|---|---|
| 主臥／次臥／臥室 | `bedroom` | 床＋衣櫃 |
| 客廳 | `living_room` | 沙發＋茶几＋電視櫃 |
| 餐廳／飯廳 | `dining_room` | 餐桌＋餐椅 |
| 廚房／陽台／浴室／儲藏 | 有對應但**類型全是死鍵** | 仍為空（見 §7） |
